# AI-SCRUM-ORIGIN-PROCESS v1：スクラムとアジャイルの原典の決まり

オーナー（人）と Claude Code がスクラムで開発するときに守る、**原典に書かれている決まりだけ** をまとめた文書。
次の 3 つの文書に書かれていることだけを載せ、このチームで足したスクラム・アジャイルの進め方は `AI-SCRUM-OPTION-PROCESS_v1.md`、スクラム・アジャイルに関係しない作業の決まりは `AI-SCRUM-TEAM-PROCESS_v1.md` に分けた。

| 原典 | 略記 | この文書での使い方 |
| :--- | :--- | :--- |
| `アジャイルソフトウェア開発宣言.md` | 宣言 | 判断に迷ったときの優先順位（4 つの価値） |
| `アジャイル宣言の背後にある原則.md` | 原則 | 決まりを作る・直すときの理由（12 の原則） |
| `スクラムガイド2020.md` | ガイド | 役割・イベント・作成物の定義（変えてはいけない骨組み） |

版：v1

## 0. この文書について

### 0.1 3 つの文書の関係

| 文書 | 中身 | 変えてよいか |
| :--- | :--- | :--- |
| `AI-SCRUM-ORIGIN-PROCESS_v1.md`（この文書） | 原典に書かれている決まり | 変えない（原典が改訂されたときだけ直す） |
| `AI-SCRUM-OPTION-PROCESS_v1.md`（OPTION） | 原典の上に、このチームで足したスクラム・アジャイルの進め方（担い手・期間・スクラムの文書の形・イベントの手順） | スプリントレトロスペクティブで変えてよい |
| `AI-SCRUM-TEAM-PROCESS_v1.md`（TEAM） | スクラム・アジャイルに関係しない、このチームの作業の決まり（Git・文書の管理・作業の手順・技術の知見） | スプリントレトロスペクティブで変えてよい |

- **優先の順は ORIGIN（この文書）→ OPTION → TEAM**。下の文書が上の文書と食い違ったら、上に従い、下を直す。
- OPTION で原典にないものを足すときは、この文書の決まりを弱めない形で足す。原典から外れるものを置くときは、OPTION に「原典との違い」として理由とともに書く。
- この文書の「チーム」「プロダクトオーナー」などは役割の名前で書く。だれが担うかは OPTION の 1 章に書く。

### 0.2 書き方

- 各節の終わりに出典を書く（例：「出典：ガイド『スプリント』」）。
- 原典の文をできるだけそのまま使い、短く言い換えたところも意味を変えない。
- 原典にない例・数値・手順は書かない。

## 1. 判断の拠り所

### 1.1 4 つの価値

私たちは、ソフトウェア開発の実践あるいは実践を手助けをする活動を通じて、よりよい開発方法を見つけだそうとしている。この活動を通して、次の価値に至った。

| # | より価値をおく（右記） | 価値はあるが相対的に低い（左記） |
| :--- | :--- | :--- |
| 1 | 個人と対話 | プロセスやツール |
| 2 | 動くソフトウェア | 包括的なドキュメント |
| 3 | 顧客との協調 | 契約交渉 |
| 4 | 変化への対応 | 計画に従うこと |

左記のことがらに価値があることを認めながらも、右記のことがらにより価値をおく。左記を否定するものではない。

出典：宣言

### 1.2 12 の原則

1. 顧客満足を最優先し、価値のあるソフトウェアを早く継続的に提供する。
2. 要求の変更はたとえ開発の後期であっても歓迎する。変化を味方につけることによって、お客様の競争力を引き上げる。
3. 動くソフトウェアを、2-3 週間から 2-3 ヶ月というできるだけ短い時間間隔でリリースする。
4. ビジネス側の人と開発者は、プロジェクトを通して日々一緒に働かなければならない。
5. 意欲に満ちた人々を集めてプロジェクトを構成する。環境と支援を与え仕事が無事終わるまで彼らを信頼する。
6. 情報を伝えるもっとも効率的で効果的な方法はフェイス・トゥ・フェイスで話をすることである。
7. 動くソフトウェアこそが進捗の最も重要な尺度である。
8. アジャイル・プロセスは持続可能な開発を促進する。一定のペースを継続的に維持できるようにしなければならない。
9. 技術的卓越性と優れた設計に対する不断の注意が機敏さを高める。
10. シンプルさ（ムダなく作れる量を最大限にすること）が本質である。
11. 最良のアーキテクチャ・要求・設計は、自己組織的なチームから生み出される。
12. チームがもっと効率を高めることができるかを定期的に振り返り、それに基づいて自分たちのやり方を最適に調整する。

出典：原則（番号は参照のために付けた）

## 2. スクラムの定義と理論

### 2.1 スクラムとは

スクラムとは、複雑な問題に対応する適応型のソリューションを通じて、人々、チーム、組織が価値を生み出すための軽量級フレームワークである。スクラムは次の環境を促進するために、スクラムマスターを必要とする。

1. プロダクトオーナーは、複雑な問題に対応するための作業をプロダクトバックログに並べる。
2. スクラムチームは、スプリントで選択した作業を価値のインクリメントに変える。
3. スクラムチームとステークホルダーは、結果を検査して、次のスプリントに向けて調整する。
4. 繰り返す。

- スクラムフレームワークは意図的に不完全であり、スクラムの理論を実現するために必要な部分のみが定義されている。
- スクラムのルールは詳細な指示ではなく、実践者の関係性や相互作用をガイドするものである。
- スクラムフレームワークの中で、さまざまなプロセス・技法・手法を使用できる。

出典：ガイド「スクラムの定義」

### 2.2 経験主義とリーン思考

- **経験主義**：知識は経験から生まれ、意思決定は観察に基づく。
- **リーン思考**：ムダを省き、本質に集中する。
- 予測可能性を最適化してリスクを制御するために、イテレーティブ（反復的）でインクリメンタル（漸進的）なアプローチをとる。
- 検査と適応のための 4 つの正式なイベントを、それらを包含する「スプリント」の中で組み合わせる。

出典：ガイド「スクラムの理論」

### 2.3 三本柱

| 柱 | 決まり |
| :--- | :--- |
| 透明性 | 創発的なプロセスや作業は、作業を実行する人とその作業を受け取る人に見える必要がある。重要な意思決定は 3 つの正式な作成物の状態に基づく。透明性のない検査は、誤解を招き、ムダである |
| 検査 | 作成物と合意されたゴールに向けた進捗状況は、頻繁かつ熱心に検査されなければならない。5 つのイベントがそのリズムを提供する。適応のない検査は意味がない |
| 適応 | プロセスや成果となるプロダクトが許容範囲を逸脱していたら、できるだけ早く調整しなければならない。スクラムチームは、検査によって新しいことを学んだ瞬間に適応する。関係者に権限が与えられていない・自己管理されていないときは、適応が難しくなる |

出典：ガイド「透明性」「検査」「適応」

### 2.4 5 つの価値基準

| 価値基準 | スクラムチームがすること |
| :--- | :--- |
| 確約（Commitment） | ゴールを達成し、お互いにサポートすることを確約する |
| 集中（Focus） | ゴールに向けて可能な限り進捗できるように、スプリントの作業に集中する |
| 公開（Openness） | スクラムチームとステークホルダーは、作業や課題を公開する |
| 尊敬（Respect） | お互いに能力のある独立した個人として尊敬し、一緒に働く人たちからも尊敬される |
| 勇気（Courage） | 正しいことをする勇気や困難な問題に取り組む勇気を持つ |

下される意思決定、実行される手順、スクラムの使用方法は、これらの価値基準を弱めるものではなく、強化させるものでなければならない。

出典：ガイド「スクラムの価値基準」

## 3. スクラムチーム

### 3.1 チーム

- スクラムチームは、スクラムマスター 1 人、プロダクトオーナー 1 人、複数人の開発者で構成される。
- サブチームや階層は存在しない。一度にひとつの目的（プロダクトゴール）に集中する。
- **機能横断型**：各スプリントで価値を生み出すために必要なすべてのスキルを備える。
- **自己管理型**：誰が何を、いつ、どのように行うかをスクラムチーム内で決定する。
- 通常は 10 人以下。大きくなりすぎたら、同じプロダクトゴール・プロダクトバックログ・プロダクトオーナーを共有する複数のスクラムチームに再編成することを検討する。
- プロダクトに関して必要となり得るすべての活動（ステークホルダーとのコラボレーション、検証、保守、運用、実験、研究開発など）に責任を持つ。
- 持続可能なペースでスプリントの作業を行う。
- スクラムチーム全体が、スプリントごとに価値のある有用なインクリメントを作成する責任を持つ。

出典：ガイド「スクラムチーム」

### 3.2 開発者

各スプリントにおいて、利用可能なインクリメントのあらゆる側面を作成することを確約する。常に次の結果に責任を持つ。

- スプリントの計画（スプリントバックログ）を作成する。
- 完成の定義を忠実に守ることにより品質を作り込む。
- スプリントゴールに向けて毎日計画を適応させる。
- 専門家としてお互いに責任を持つ。

出典：ガイド「開発者」

### 3.3 プロダクトオーナー

スクラムチームから生み出されるプロダクトの価値を最大化することの結果に責任を持つ。効果的なプロダクトバックログ管理にも責任を持つ。

- プロダクトゴールを策定し、明示的に伝える。
- プロダクトバックログアイテムを作成し、明確に伝える。
- プロダクトバックログアイテムを並び替える。
- プロダクトバックログに透明性があり、見える化され、理解されるようにする。

- 上記の作業は他の人に委任できるが、**最終的な責任はプロダクトオーナーが持つ**。
- 組織全体でプロダクトオーナーの決定を尊重しなければならない。決定は、プロダクトバックログの内容や並び順、スプリントレビューでの検査可能なインクリメントによって見える化される。
- プロダクトオーナーは 1 人の人間であり、委員会ではない。ステークホルダーがプロダクトバックログを変更したいときは、プロダクトオーナーを説得する。
- スプリントを中止する権限を持つのはプロダクトオーナーだけである（4.1）。

出典：ガイド「プロダクトオーナー」「スプリント」

### 3.4 スクラムマスター

スクラムガイドで定義されたスクラムを確立させることの結果に責任を持つ。スクラムチームの有効性に責任を持つ。スクラムチームと、より大きな組織に奉仕する真のリーダーである。

**スクラムチームへの支援**
- 自己管理型で機能横断型のチームメンバーをコーチする。
- 完成の定義を満たす価値の高いインクリメントの作成に集中できるよう支援する。
- スクラムチームの進捗を妨げる障害物を排除するように働きかける。
- すべてのスクラムイベントが開催され、ポジティブで生産的であり、タイムボックスの制限が守られるようにする。

**プロダクトオーナーへの支援**
- 効果的なプロダクトゴールの定義とプロダクトバックログ管理の方法を探すことを支援する。
- 明確で簡潔なプロダクトバックログアイテムの必要性についてスクラムチームに理解してもらう。
- 複雑な環境での経験的なプロダクト計画の策定を支援する。
- 必要に応じてステークホルダーとのコラボレーションを促進する。

**組織への支援**
- 組織へのスクラムの導入を指導・トレーニング・コーチする。
- 組織においてスクラムの実施方法を計画・助言する。
- 複雑な作業に対する経験的アプローチを社員やステークホルダーに理解・実施してもらう。
- ステークホルダーとスクラムチームの間の障壁を取り除く。

出典：ガイド「スクラムマスター」

## 4. スクラムイベント

**共通の決まり**
- スプリントは他のすべてのイベントの入れ物である。各イベントは、作成物の検査と適応をするための公式の機会である。
- 規定通りにイベントを運用しなければ、検査と適応の機会が失われる。
- イベントは規則性を生み、スクラムで定義されていない会議の必要性を最小限に抑える。
- すべてのイベントは、複雑さを低減するために、同じ時間と場所で開催されることが望ましい。

出典：ガイド「スクラムイベント」

### 4.1 スプリント

- スプリントにおいてアイデアが価値に変わる。
- 一貫性を保つため、**1 か月以内の決まった長さ** とする。前のスプリントが終わり次第、新しいスプリントが始まる。
- プロダクトゴールを達成するために必要なすべての作業（スプリントプランニング、デイリースクラム、スプリントレビュー、スプリントレトロスペクティブを含む）は、スプリント内で行う。

スプリントでは、
- スプリントゴールの達成を危険にさらすような変更はしない。
- 品質を低下させない。
- プロダクトバックログを必要に応じてリファインメントする。
- 学習が進むにつれてスコープが明確化され、プロダクトオーナーとの再交渉が必要になる場合がある。

- 期間が長すぎると、スプリントゴールが役に立たなくなり、複雑さが増し、リスクが高まる。短くすれば、学習サイクルが増え、リスクを短い時間枠に収められる。
- バーンダウン・バーンアップ・累積フローなどの見通しのプラクティスは、経験主義の重要性を置き換えるものではない。すでに発生したことだけが、将来を見据えた意思決定に使用できる。
- スプリントゴールがもはや役に立たなくなった場合、スプリントは中止されることがある。**プロダクトオーナーだけが中止する権限を持つ**。

出典：ガイド「スプリント」

### 4.2 スプリントプランニング

スプリントの起点であり、スプリントで実行する作業の計画を、スクラムチーム全体の共同作業で立てる。

- プロダクトオーナーは、最も重要なプロダクトバックログアイテムとプロダクトゴールとの関連性について話し合う準備ができているかを確認する。
- アドバイスをもらうために、チーム以外の人を招待してもよい。

| トピック | 決まり |
| :--- | :--- |
| 1：このスプリントはなぜ価値があるのか？ | プロダクトオーナーが、プロダクトの価値と有用性をどう高められるかを提案する。スクラムチーム全体で、ステークホルダーに価値を伝えるスプリントゴールを定義する。スプリントゴールはスプリントプランニングの終了までに確定する |
| 2：このスプリントで何ができるのか？ | 開発者が、プロダクトオーナーとの話し合いを通じて、プロダクトバックログからアイテムを選択する。この中でリファインメントをしてもよい。過去のパフォーマンス・今回のキャパシティ・完成の定義の理解を深めれば、予測に自信が持てるようになる |
| 3：選択した作業をどのように成し遂げるのか？ | 開発者が、完成の定義を満たすインクリメントを作成するために必要な作業を計画する。多くの場合、アイテムを 1 日以内の小さな作業アイテムに分解する。どう行うかは **開発者だけの裁量** |

- スプリントゴール、選択したアイテム、それらを提供するための計画をまとめて **スプリントバックログ** と呼ぶ。
- タイムボックス：1 か月のスプリントで最大 8 時間。短いスプリントでは短くすることが多い。

出典：ガイド「スプリントプランニング」

### 4.3 デイリースクラム

- 目的：計画された今後の作業を調整しながら、スプリントゴールに対する進捗を検査し、必要に応じてスプリントバックログを適応させる。
- スクラムチームの **開発者のための 15 分** のイベント。スプリント期間中は毎日、同じ時間・場所で開催する。
- プロダクトオーナーまたはスクラムマスターがスプリントバックログのアイテムに積極的に取り組んでいる場合は、開発者として参加する。
- 開発者は、スプリントゴールの進捗に焦点をあて、これからの 1 日の実行可能な計画を作成する限り、構造とやり方を選択できる。
- コミュニケーションを改善し、障害物を特定し、迅速な意思決定を促進する。
- 開発者が計画を調整できるのは、デイリースクラムのときだけではない。

出典：ガイド「デイリースクラム」

### 4.4 スプリントレビュー

- 目的：スプリントの成果を検査し、今後の適応を決定する。
- スクラムチームが、主要なステークホルダーに作業の結果を提示し、プロダクトゴールに対する進捗について話し合う。
- スプリントで何が達成され、環境で何が変化したかをレビューし、次にやるべきことに協力して取り組む。プロダクトバックログを調整することもある。
- **ワーキングセッション** であり、プレゼンテーションだけに限定しない。
- スプリントの最後から 2 番目のイベント。タイムボックスは 1 か月のスプリントで最大 4 時間。短いスプリントでは短くすることが多い。

出典：ガイド「スプリントレビュー」

### 4.5 スプリントレトロスペクティブ

- 目的：品質と効果を高める方法を計画する。
- 個人、相互作用、プロセス、ツール、完成の定義に関して、今回のスプリントがどう進んだかを検査する。
- スクラムチームを迷わせた仮説があれば特定し、その真因を探求する。何がうまくいったか、どのような問題が発生したか、それらがどう解決されたか（または解決されなかったか）を話し合う。
- 効果を改善するために最も役立つ変更を特定し、最も影響の大きな改善はできるだけ早く対処する。次のスプリントのスプリントバックログに追加することもできる。
- **スプリントレトロスペクティブをもってスプリントは終了する**。タイムボックスは 1 か月のスプリントで最大 3 時間。短いスプリントでは短くすることが多い。

出典：ガイド「スプリントレトロスペクティブ」

## 5. 作成物と確約

作成物は作業や価値を表し、重要な情報の透明性を最大化するよう設計されている。各作成物には、透明性と集中を高め、進捗を測定できるようにする「確約（コミットメント）」が含まれる。

| 作成物 | 確約 |
| :--- | :--- |
| プロダクトバックログ | プロダクトゴール |
| スプリントバックログ | スプリントゴール |
| インクリメント | 完成の定義 |

これらの確約は、スクラムチームとステークホルダーの経験主義とスクラムの価値基準を強化するために存在する。

出典：ガイド「スクラムの作成物」

### 5.1 プロダクトバックログ

- 創発的かつ順番に並べられた、プロダクトの改善に必要なものの一覧。スクラムチームが行う作業の **唯一の情報源**。
- 1 スプリント内で完成できるアイテムは、スプリントプランニングのときには選択の準備ができている。
- **リファインメント**：アイテムをより小さく詳細になるように分割・定義する、継続的な活動。説明・並び順・サイズなどの詳細を追加する。属性は作業領域によって異なる。
- 作業を行う **開発者が、作業規模の評価に責任を持つ**。プロダクトオーナーは、開発者がトレードオフを理解して選択できるよう支援できる。

出典：ガイド「プロダクトバックログ」

### 5.2 プロダクトゴール

- プロダクトの将来の状態を表し、スクラムチームの計画のターゲットになる。プロダクトバックログに含まれる。
- プロダクトバックログの残りの部分は、プロダクトゴールを達成する「何か（what）」を定義する。
- スクラムチームの長期的な目標。**次の目標に移る前に、ひとつの目標を達成（または放棄）しなければならない**。
- プロダクトとは価値を提供する手段である。明確な境界、既知のステークホルダー、明確に定義されたユーザーや顧客を持つ。

出典：ガイド「確約（コミットメント）：プロダクトゴール」

### 5.3 スプリントバックログ

- スプリントゴール（なぜ）、選択されたプロダクトバックログアイテム（何を）、インクリメントを届けるための実行可能な計画（どのように）で構成される。
- **開発者による、開発者のための計画**。スプリントで行う作業がリアルタイムに反映され、学ぶにつれてスプリントの期間を通して更新される。
- デイリースクラムで進捗を検査できる程度の詳細さが必要である。

出典：ガイド「スプリントバックログ」

### 5.4 スプリントゴール

- スプリントの唯一の目的。開発者が確約するものだが、達成に必要な作業に対しては柔軟性をもたらす。
- 一貫性と集中を生み出し、スクラムチームに一致団結した作業を促す。
- スプリントプランニングで作成され、スプリントバックログに追加される。
- 作業が予想と異なることが判明した場合は、スプリントゴールに影響を与えないように、**プロダクトオーナーと交渉してスプリントバックログのスコープを調整する**。

出典：ガイド「確約（コミットメント）：スプリントゴール」

### 5.5 インクリメント

- プロダクトゴールに向けた具体的な踏み石。これまでのすべてのインクリメントに追加し、すべてが連携して機能することを徹底的に検証する。
- 価値を提供するには、インクリメントを利用可能にしなければならない。
- スプリントでは、複数のインクリメントを作成可能である。まとめたものをスプリントレビューで提示する。
- スプリント終了前にステークホルダーにデリバリーしてもよい。**スプリントレビューを価値をリリースするための関門と見なさない**。
- **完成の定義を満たさない限り、作業をインクリメントの一部と見なすことはできない**。

出典：ガイド「インクリメント」

### 5.6 完成の定義

- プロダクトの品質基準を満たすインクリメントの状態を示した正式な記述。
- プロダクトバックログアイテムが完成の定義を満たしたときにインクリメントが誕生する。
- 作業が完了してインクリメントの一部となったことを全員の共通認識にし、透明性を生む。
- 完成の定義を満たしていないアイテムは、**リリースできず、スプリントレビューで提示することもできない**。あとで検討できるようにプロダクトバックログに戻す。
- 組織の標準があれば、すべてのスクラムチームは最低限それに従う。なければ、スクラムチームがプロダクトに適した完成の定義を作成する。
- 開発者は完成の定義に準拠する。プロダクトに関わるスクラムチームが複数あれば、共通の完成の定義を作成して準拠する。

出典：ガイド「確約（コミットメント）：完成の定義」

## 6. フレームワークは変えない

- スクラムフレームワークは不変である。一部だけを導入することも可能だが、それはスクラムとは言えない。
- すべてを備えたものがスクラムであり、その他の技法・方法論・プラクティスの入れ物として機能する。
- スクラムの核となるデザインやアイデアを変更したり、要素を省略したり、ルールに従わなかったりすると、問題が隠蔽され、スクラムの利点が制限される。
- スクラムと適合するパターン・プロセス・インサイトは、スクラムガイドの範囲外であり、状況によって異なる（このチームのものは OPTION に書く）。

出典：ガイド「最後に」「スクラムガイドの目的」
