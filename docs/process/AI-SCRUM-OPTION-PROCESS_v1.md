## 0. この文書について

### 0.1 3 つの文書の関係

- **優先の順は ORIGIN → OPTION → TEAM**。下の文書が上の文書と食い違ったら、上に従い、下を直す。
- この文書は、ORIGIN の骨組みの上に、このチームの担い手・期間・スクラムの文書の形・イベントの手順を足したもの。ORIGIN の決まりを弱めない。
- Git・PR・文書の ID・技術のやり方など、スクラムでなくても同じになるものは TEAM に書き、この文書には書かない。
- この文書と TEAM はスプリントレトロスペクティブで変えてよい（冒頭の「版」を上げる）。ORIGIN は変えない。

### 0.2 原典との違い（原典にない・原典から外れるもの）

| このチームの決まり | 原典との関係 | 理由 |
| :--- | :--- | :--- |
| スプリントゼロ（6.1） | **原典から外れる**。ガイドにスプリントゼロはなく、スプリントは毎回インクリメントを作る（ORIGIN 2.1・3.1）。スプリントゼロはインクリメントを作らない | 始める前に、なぜ・何を・どう作るかをオーナーとそろえるため。スプリントではなく準備の期間として扱い、1 週間までに限る |
| インセプションデッキ（5.7） | 原典にない（『アジャイルサムライ』の手法） | スプリントゼロでそろえることを、10 の問いで漏れなく確かめるため |

| ふりかえりを YWT で書く（8 章） | 原典にない | SDD-PROCESS v3 から引き継いだ書き方 |

### 0.3 SDD-PROCESS v3 から変わったこと

| 観点 | SDD-PROCESS v3 | OPTION・TEAM |
| :--- | :--- | :--- |

| 進め方 | 00〜06 の文書を工程順に全部作ってから実装する | 1 週間のスプリントをくり返し、毎回インクリメントを作る |

## 1. チームの体制

スクラムチームは 1 つで、1 つのプロダクトに集中する（ORIGIN 3.1）。

| 責任 | 担う人 | 原典の責任 | このチームで足したこと |
| :--- | :--- | :--- | :--- |
| プロダクトオーナー（PO） | オーナー（人） | ORIGIN 3.3 | 本番に公開するか・いつかを決める（6.7）。PBI の受け入れをスプリントレビューで決める（6.6） |
| 開発者 | Claude Code | ORIGIN 3.2 | スプリントの中は TASK ごとに指示を待たずに進める（2 章） |
| スクラムマスター（SM） | Claude Code（ORIGIN とこの文書が基準） | ORIGIN 3.4 | PO の作業の下書き・整理を引き受ける（1.1）。オーナーの決定待ちを作業セッションごとに見える化する（6.3） |

### 1.1 プロダクトオーナーの支援

ORIGIN 3.3（委任しても最終的な責任は PO）と ORIGIN 3.4（SM の PO への支援）にもとづき、Claude Code は PO の作業の下書き・調べもの・整理を引き受け、**PO が決めるだけでよい状態**にして渡す。決めるのはいつもオーナー。

| 支援すること | Claude Code がすること | オーナー（PO）が決めること |
| :--- | :--- | :--- |
| インセプションデッキを作る | 10 の問いの答えの案を先に書き、分からないことを聞くことの一覧にする。話し合いを進め、決まったことをまとめる（6.1） | 各問いの答え、トレードオフの優先順位 |
| プロダクトゴールを定める | 仕様書・オーナーの話から、ゴールの案を 2〜3 通り書く（誰の・どんな状態か・達成の確かめ方）。ゴールに入らないものを「作らないもの」として示す | どのゴールにするか |
| PBI を書く | オーナーの思いつき・メモ・レビューでの感想を PBI の形（ストーリー・受け入れ条件）にする。1 つの PBI に 2 つの目的が混ざっていたら分ける案を出す | 中身と受け入れ条件でよいか |
| 受け入れ条件を明確にする | あいまいな言葉（「すばやく」「見やすく」）を、確かめられる条件（数値・画面の状態）に言い換える案を出す | どの条件にするか |
| 並び順を決める | 価値・リスク・依存・大きさを並べた表と、並べ替えの案を出す。**価値の理由と作る手間を分けて書く**。並び順を確かめるときは、**プロダクトバックログの表をメッセージに出してから聞く**（オーナーがファイルを見に行く時間を減らす。v1.3） | 並び順 |
| プロダクトバックログを整える | 古くなった PBI・重なる PBI・ゴールに関係しない PBI を見つけ、取り下げ・統合の案を出す。上位 1〜2 スプリント分が「準備 OK」になるよう、先回りしてリファインメントを進める | 取り下げ・統合してよいか |
| 進み具合から計画を立てる | 完成した PBI の数の実績から、プロダクトゴールに届く見込み（あと何スプリントか、幅を持たせて）を示す。見込みは実績だけから出し、願望で縮めない | 範囲を削るか・ゴールを変えるか |
| 決める材料を集める | 似たアプリの作り・技術の制約・費用など、決めるのに要る情報を調べて短くまとめる。確かめていないことは「確かめていない」と書く | — |
| 関係者との協力 | 関係者（使う人・家族・仲間など）に見てもらうときの案内文、聞くことの一覧、もらった意見の整理（PBI の案に直す）を用意する | 誰に見てもらうか・どの意見を取り入れるか |
| スプリントレビューを準備する | できたもの・できなかったもの・ゴールまでの見込み・決めてほしいことを 1 画面にまとめる | 受け入れるか・次に何をするか |
| リリースを判断する | 公開に入るもの・入らないもの・利用者にとって何が変わるかをまとめる | 公開するか・いつか |

**支援の決まり**
- 案は **選択肢と推奨** で出し、推奨の理由（利用者にとっての価値）を先に書く。案が 1 つしかないときも、「やらない」という選択肢を並べる。
- オーナーが決めていないことを、決まったものとして文書に書かない。案の段階では `status: review` のままにし、プロダクトバックログの並び順も、オーナーの返事があるまで変えない。
- オーナーの思いつきは、その場で PBI の案（`未整理`）にして残す。今のスプリントに入れるかは聞かずに決めつけない（9 章）。
- 決めてほしいことは、まとめて 1 回で聞く。急ぎのものだけ作業の途中で聞く。
- オーナーが「任せる」と言ったことも、決めた内容と理由を伝えて記録に残す（あとで見直せるように）。

**開発者が PO を支援することへの備え**
開発者でもある Claude Code が並び順の案を出すと、作りやすいもの・作りたいものを上に置きやすい。そこで次のようにする。
- 並び順の案では、**利用者にとっての価値** と **作る手間** を別の列に書き、手間を理由に価値の高いものを下げるときはそう明記する。
- 技術的に面白いだけの PBI、先回りの仕組みの PBI を、自分から足さない（ORIGIN 1.2 の原則 10）。必要だと考えるときは、利用者にとって何がよくなるかを書いて案にする。

**同じ者が開発者・スクラムマスター・PO の支援を兼ねることへの備え**
Claude Code がこれらを担うと、自分の作業のためにタイムボックスや完成の定義を甘くしたり、PO の決定を誘導したりしやすい。そこで次のようにする。
- 完成の定義のうち機械で確かめられるものは、CI と `check:docs` に入れて自動で止める（7 章・TEAM 4.5）。
- スプリントレトロスペクティブの最初に「ORIGIN・OPTION・TEAM どおりに進めたか」「PO の決定を代わりにしていないか」を確かめる（8 章）。
- オーナーは、人のスクラムマスターを別に置いてもよい。置いたときは、1 章の表を書き換える。

**オーナーが使う時間（1 週間のスプリントの目安）**
スプリントプランニング・スプリントレビュー・スプリントレトロスペクティブへの参加、プレビューでの実機確認、PR のマージ、決めてほしいことへの返事。PO の作業の下書きは Claude Code が受け持つので、オーナーは主に **案を読んで決めること** に時間を使う。合わせて 3〜4 時間ほど。持続可能なペース（ORIGIN 1.2 の原則 8）を保つため、これを大きく超えそうなときは Claude Code がプランニングで確認や決定の依頼を減らす案を出す。

## 2. 基本の決まり

Git・PR・言葉づかいなどの作業の決まりは TEAM 1 章。

| 決まり | 内容 |
| :--- | :--- |
| 決める人を分ける | ORIGIN 7.2 の分担に、このチームの分担（2.1）を足す |
| スプリントの中は自分で進む | スプリントゴールに合意したあとは、Claude Code はスプリントバックログの TASK を順に自分で進める。TASK ごとに指示を待たない |
| 止まるところ | PR のマージを頼むとき／PO が決めることが出たとき／スプリントゴールが危うくなったとき／スプリントの終わり（レビュー） |
| 本番はリリースでだけ | main へのマージはプレビューにだけ公開される（TEAM 1 章）。本番の公開は、完成の定義を満たした PBI について、PO の指示で行う（6.7） |

### 2.1 このチームで足した分担

ORIGIN 7.2 に書かれていない決定の分担。

| PO（オーナー）が決める | 開発者（Claude Code）が決める |
| :--- | :--- |
| PBI の中身・受け入れ条件 | 技術・設計・ファイルの構成（ADR に残す） |
| 画面の見た目・文言（GUI） | 選んだ PBI を TASK に分けること、その順番 |
| できたものを受け入れるか（スプリントレビュー） | テストの書き方・確認 ID の割り当て |
| 本番に公開するか・いつか | 完成の定義を満たしたかの判断（定義そのものの変更は PO と合意） |
| インセプションデッキの答え・トレードオフの優先順位 | — |

PO が決めることも、案を作るのは Claude Code（1.1）。オーナーは案を見て決める。

技術の決定のうち、**PO の前提を変えるもの**（お金がかかる・公開先・データの置き場所・対象の端末・オフラインで動くか）は、決める前に選択肢と推奨を示して PO に聞く。

## 3. 価値と原則の当てはめ

ORIGIN 1 章・2.4 の価値と原則を、このチームでどう使うか。

### 3.1 4 つの価値（ORIGIN 1.1）の使い方

| より価値をおく | このチームでの選び方 |
| :--- | :--- |
| 個人と対話 | 文書の決まりより、オーナーとの対話で確かめることを先にする。決まりがオーナーの役に立っていなければ、レトロスペクティブで OPTION・TEAM を変える |
| 動くソフトウェア | 文書は「次の作業に必要な分」だけ書く。進み具合は文書の量ではなく、プレビューで動くもので示す |
| 顧客との協調 | 受け入れ条件は約束事ではなく、レビューで一緒に見直す出発点 |
| 変化への対応 | プロダクトバックログはいつでも並べ直せる（9 章） |

### 3.2 5 つの価値基準（ORIGIN 2.4）を Claude Code の振る舞いにすると

| 価値基準 | Claude Code がすること |
| :--- | :--- |
| 確約 | スプリントゴールを達成するために動く。できそうにないと分かったら、すぐ PO に伝えて話し合う |
| 集中 | スプリントバックログにない作業を勝手に始めない。気づいた改善は PBI の案としてプロダクトバックログに書く |
| 公開 | 失敗・推測・確かめていないことを隠さない。テストが落ちたら出力ごと伝える |
| 尊敬 | オーナーの決定を尊重する。専門の言葉で煙に巻かない |
| 勇気 | 仕様や計画の問題に気づいたら、言いにくくても理由を添えて伝える。「分からない」と言う |

### 3.3 12 の原則（ORIGIN 1.2）がどこにあるか

| # | 原則（要約） | OPTION・TEAM での形 |
| :--- | :--- | :--- |
| 1 | 価値のあるソフトウェアを早く継続的に | 毎スプリントのインクリメントと AC（5.6） |
| 2 | 要求の変更を歓迎 | プロダクトバックログの変更（9 章） |
| 3 | 短い間隔でリリース | 1 週間のスプリント、完成の定義を満たせばいつでもリリース（6.7） |
| 4 | ビジネス側と開発者が日々一緒に | PO の決定待ちを作業セッションごとに伝える（6.3） |
| 5 | 意欲ある人を信頼して任せる | スプリントの中は TASK ごとに指示を待たない（2 章） |
| 6 | 顔を合わせて話す | 文書の往復より、チャットで直接聞いて決め、決めたことだけを文書に残す |
| 7 | 動くソフトウェアが進捗の尺度 | 進捗はプレビューで動く PBI の数で示す |

| 11 | 自己組織的なチーム | 「どう作るか」は Claude Code が決める（2.1） |
| 12 | 定期的にふりかえって調整 | YWT のふりかえりと、OPTION・TEAM の改訂（8 章） |

## 5. スクラムの文書

ORIGIN 5 章の作成物と確約を、このチームではどの文書に書くか。ID・ファイル名・frontmatter・番号・版の決まりと、スクラム以外の文書（設計・テストなど）は TEAM 2 章。

| 作成物（ORIGIN 5 章） | 確約 | 置き場所 |
| :--- | :--- | :--- |
| プロダクトバックログ | プロダクトゴール | `docs/00-product/` |
| スプリントバックログ | スプリントゴール | `docs/06-sprints/sprint-<2 桁>/sprint-backlog.md` |
| インクリメント | 完成の定義 | `docs/definition-of-done.md`（記録は `docs/07-increments/`） |

### 5.1 種類と PO の承認

| 種類 | 略 | 置き場所 | いつ作る | PO の承認 |
| :--- | :--- | :--- | :--- | :--- |
| inception-deck | IDK | docs/00-product | スプリントゼロ。前提が変わったとき（5.7） | あり |
| product-goal | PG | docs/00-product | スプリントゼロ。ゴールを変えるとき | あり |
| product-backlog | （ID なし） | docs/00-product/product-backlog.md | スプリントゼロ。以後いつでも | 並び順は PO が決める |
| product-backlog-item | PBI | docs/01-pbi | 思いついたとき（未整理で可）。リファインメントで詳しくする | 「準備 OK」にするとき |
| sprint-backlog（TASK を含む） | （ID なし） | docs/06-sprints/sprint-<2 桁> | スプリントプランニング | スプリントゴールは合意 |
| attested-computation（インクリメントの実施記録） | AC | docs/07-increments | PBI が完成の定義を満たしたとき | あり（スプリントレビューで受け入れ） |
| definition-of-done | （ID なし） | docs/definition-of-done.md | スプリントゼロ。変えるのはレトロスペクティブで | 変えるときは合意 |

ID のないそのほかのスクラムの文書：スプリントのレビュー `docs/06-sprints/sprint-<2 桁>/review.md`、レトロスペクティブ `docs/06-sprints/sprint-<2 桁>/retrospective.md`、全体のまとめ `docs/06-sprints/summary.md`。

TASK はファイルを作らず、スプリントバックログの表に書く。

**epic について**：大きなまとまりは、PBI の `theme`（テーマ）に名前を書いて表す。ファイルは作らない。

### 5.2 プロダクトゴールの書き方

決まりは ORIGIN 5.2。1〜3 文で書く。

```markdown
# <PREFIX>-PG-0001 プロダクトゴール

<誰が>、<どんなとき>に、<何ができる>状態にする。

- 対象の利用者：…
- 対象の端末・公開先：…
- 作らないもの：…（仕様書の範囲外。インセプションデッキの「やらないことリスト」）
- 達成をどう確かめるか：…（仕様書の受け入れ基準の §x がすべて完成している、など）
```

sources に、インセプションデッキ（IDK）と仕様書の版を書く。ゴールの文は、インセプションデッキの「エレベーターピッチ」と「パッケージデザイン」から作る。

### 5.3 プロダクトバックログの書き方

決まりは ORIGIN 5.1。ここにない作業はしない。

```markdown
# プロダクトバックログ

プロダクトゴール：<PREFIX>-PG-0001（v1.0）
更新：2026-11-02

| 順 | ID | 題名 | テーマ | 大きさ | 状態 |
| ---: | :--- | :--- | :--- | :--- | :--- |
| 1 | <PREFIX>-PBI-0001 | タイトル画面から始める | 基本操作 | S | 準備 OK |
| 2 | <PREFIX>-PBI-0004 | … | … | M | 未整理 |
```

- **順** は PO が決める（ORIGIN 3.3）。Claude Code は並べ替えの案を出す（1.1）。
- **大きさ** は開発者が見積もる（ORIGIN 5.1）。このチームでは S：1〜2 TASK、M：3〜5 TASK、L：1 スプリントに収まらない → 分ける。
- **状態**：`未整理` → `準備 OK` → `スプリント中` → `完成`（完成の定義を満たした）→ `リリース済み`。やめたものは `取り下げ`（行は消さない）。

### 5.4 PBI（プロダクトバックログアイテム）の書き方

frontmatter は TEAM 2.2 の形（`type: product-backlog-item`、`theme` を足す。`status: stable` = PO が「準備 OK」と認めた）。

本文に書くこと：
- **ストーリー**：<誰>として、<何>がしたい。それは<なぜ>だから。
- **受け入れ条件**：PO が見て「できた」と言える条件。1 つごとに確認 ID（TEAM 2.3）を付ける。
- **画面**：関わる GUI の ID（なければ「なし」）。
- **メモ**：PO と話して決めたこと、分からないこと、変更の影響の一覧（9 章）。

### 5.5 スプリントバックログの書き方

決まりは ORIGIN 5.3・5.4。

```markdown
# スプリント 03 のスプリントバックログ

期間：2026-11-09 〜 2026-11-15（1 週間）
プロダクトゴール：<PREFIX>-PG-0001（v1.0）

## スプリントゴール
<このスプリントが、なぜ価値があるか。1〜2 文>

## 選んだ PBI
| ID | 題名 | 状態 |
| :--- | :--- | :--- |
| <PREFIX>-PBI-0004 | … | スプリント中 |

## 計画（TASK）
| ID | やること | PBI | 確認 ID | 依存 | ブランチ | 状態 | PR |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| <PREFIX>-TASK-0012 | … | PBI-0004 | TC-0004-01, 02 | — | feat/TASK-0012-… | 済 | #34 |

## レトロスペクティブから入れた改善
- 前回の T：…

## 作業セッションの記録（デイリースクラム）
- 2026-11-10：ゴールまで 2/4 TASK。今日は TASK-0013。妨げ：GUI の文言を PO に確認中
```

### 5.6 AC（インクリメントの実施記録）

インクリメントの決まりは ORIGIN 5.5。このチームでは、インクリメントになったことを AC に記録する。

- AC は PBI ごとに 1 つ。番号は PBI と同じ（TEAM 2.3）。sources に PBI・TC・関わった TASK を書く。
- 書くこと：自動テストの結果（数値・文言はテストの実際の出力どおり）、プレビューでの実機確認の結果、「確認できなかったこと」（持っていない端末など）。

### 5.7 インセプションデッキ

プロダクトを始める前に、「なぜ作るのか・何を作るのか・どう作るのか・どれだけかかるのか」をオーナーと Claude Code で確かめ合うための 10 の問い（『アジャイルサムライ』の Jonathan Rasmusson による手法。原典にはない）。スプリントゼロで作り、プロダクトゴール・プロダクトバックログ・完成の定義の根拠にする。

置き場所：`docs/00-product/<PREFIX>-IDK-0001-inception-deck-ja.md`。frontmatter は TEAM 2.2 の形（`type: inception-deck`、sources に仕様書の版）。PO の承認あり。

| # | 問い | 答えること | 使うところ |
| :--- | :--- | :--- | :--- |
| 1 | 我われはなぜここにいるのか | 作る理由、誰のどんな困りごとを解くか、うまくいったら何が変わるか | プロダクトゴール、並び順の価値の理由 |
| 2 | エレベーターピッチを作る | 「<困りごと>を抱えている<対象の利用者>向けの、<プロダクト名>は<分類>です。これは<大事な利点>ができ、<ほかのやり方>とは違って<違い>が備わっている」の形で 30 秒 | プロダクトゴールの文 |
| 3 | パッケージデザインを作る | 箱（アプリの紹介ページ）に書く、名前・キャッチコピー・利用者にとってうれしいこと 3 つ | プロダクトゴール、上位の PBI、README |
| 4 | やらないことリストを作る | 「やる」「やらない」「あとで決める」の 3 つに分けた一覧 | プロダクトゴールの「作らないもの」、PBI を足すときの判断 |
| 5 | 「ご近所さん」を探せ | 関わる人（使う人・家族・仲間・権利を持つ人など）と、関わる外部のもの（公開先・外部サービス・ほかのアプリ） | スプリントレビューに呼ぶ人、ADR の前提 |
| 6 | 解決案を描く | おおまかな仕組みの図（端末・アプリ・保存先・公開先）と、使う技術の候補 | SA・TS の初版、PO の前提を変える ADR |
| 7 | 夜も眠れなくなるような問題は何だろう | 心配ごと（技術・端末・権利・時間など）と、それぞれの手当て | 心配の大きいものを確かめる PBI を上に置く、完成の定義 |
| 8 | 期間を見極める | 最初に公開できるまでの見込み（スプリントの数を幅で）、そこで何ができているか | リリースの見込み、スプリントレビューの見通し |
| 9 | 何を諦めるのかをはっきりさせる | トレードオフスライダー（下）で、迷ったときに何を優先するか | スコープを削るか・期間を延ばすかの判断（6.6） |
| 10 | 何がどれだけ必要なのか | オーナーが使える時間、Claude Code の使い方、道具・サービス・お金 | 1.1 のオーナーの時間、スプリントの長さ、入る量 |

**トレードオフスライダー（問い 9）**
スコープ（作る機能）・期間・費用（お金とオーナーの時間）に、1〜3 の優先順位を重ならないように付ける。**品質はスライダーに入れない**（スプリントでは品質を低下させない。ORIGIN 4.1・5.6）。

| 項目 | 優先順位（1 = いちばん守る） |
| :--- | :--- |
| スコープ | 例：3（削ってよい） |
| 期間 | 例：2 |
| 費用 | 例：1（増やさない） |
| 品質 | 動かさない（完成の定義） |

**見直すとき**：プロダクトゴールを変えるとき、トレードオフの優先順位が変わったとき、心配ごと（問い 7）が起きた・消えたとき。スプリントレビューで Claude Code が見直すかを聞く。中身が変わったら版を上げて再承認し、プロダクトゴール・プロダクトバックログへの影響を見る。

## 6. 進め方

各手順の中の Git・PR の操作（ブランチを切る・コミット・PR・マージ後の片付け）は TEAM 1 章に従う。

### 6.0 このチームのタイムボックス

ORIGIN 4 章・7.1 の上限の中で、このチームでは次のように決める。スプリントは **1 週間**（オーナーの暦で数える）。変えるときは ORIGIN 4.1 の範囲で、スプリントの途中では変えない。前のスプリントが終わったら、プランニングの指示を受けたところから次のスプリントの作業を始める。

| イベント | 出る人 | タイムボックス（1 週間のスプリント） |
| :--- | :--- | :--- |
| スプリントゼロ（最初の 1 回だけ。0.2） | スクラムチーム（関係者を呼んでよい） | 1 週間まで（オーナーとのやりとりは合わせて 4 時間まで） |
| スプリント | スクラムチーム | 1 週間 |
| スプリントプランニング | スクラムチーム | 2 時間まで |
| デイリースクラム | 開発者・POアシスタント・スクラムマスター（PO は読むだけでよい） | 15 分まで（作業セッションごと） |
| スプリントレビュー | スクラムチーム（関係者を呼んでよい） | 1 時間まで |
| スプリントレトロスペクティブ | スクラムチーム | 45 分まで |

タイムボックスはオーナーとのやりとりの時間で数える。超えそうなときは、Claude Code（スクラムマスター）が残りの論点を示し、続けるか次に回すかを聞く。

**イベントの対話と発言の記録**（v1.1。スプリント 01 のふりかえりで PO が決めた）
- どのイベントも、PO（オーナー）・POアシスタント・スクラムマスター・開発者の 4 者の対話で行う。POアシスタント・スクラムマスター・開発者は Claude Code が務め、それぞれの視点で話す（POアシスタント＝利用者の価値・並び順、スクラムマスター＝進め方・決まり・オーナーの時間、開発者＝作りやすさ・技術・リスク）。同じことの言い直しで回数を埋めない。
- スプリントプランニング・スプリントレビュー・スプリントレトロスペクティブは、4 者の発言を合わせて **最低 20 回** の対話をする。デイリースクラムは回数を決めない。
- 発言は、イベントの文書（スプリントバックログ・`review.md`・`retrospective.md`）の「発言の記録」の表（発言した人｜発言）に残す。発言した人は「PO（オーナー）」「POアシスタント（Claude Code）」「スクラムマスター（Claude Code）」「開発者（Claude Code）」で書く。PO の発言は原文のまま引く。

### 6.1 スプリントゼロ（最初の 1 回）

開始：「スプリントゼロを始めてください」（仕様書、対象の端末、公開先、使いたい／使いたくない技術、オーナーが使える時間）

**位置づけ**：原典から外れる（0.2）。スプリントを始めるための準備の期間として扱い、1 週間を超えて長引かせない。設計を先回りして作り込む場にしない（土台づくりは最初のスプリントで、触れるものと一緒に作る。6.2）。

**① インセプションデッキ（5.7）**
- [ ] `docs/sprint-00-inception` で作業する
- [ ] 仕様書を読み、10 の問いすべての答えの案を Claude Code が先に書く（1.1）。仕様書に書いていないことは、推測で埋めず「オーナーに聞くこと」として印を付ける
- [ ] **前半（問い 1〜5：なぜ・何を）** をオーナーと話し合う。エレベーターピッチは 2〜3 通り、やらないことリストは「やる・やらない・あとで決める」の案を出して選んでもらう
- [ ] **後半（問い 6〜10：どう・どれだけ）** をオーナーと話し合う。解決案は図と候補の技術を、選択肢と推奨で示す。期間は幅で示し、願望で縮めない。トレードオフスライダーはオーナーが決める
- [ ] 関わる人（問い 5）に見てもらう場合は、案内文と聞くことの一覧を用意する
- [ ] インセプションデッキを `status: review` で書き、承認を受ける

**② プロダクトゴール**
- [ ] インセプションデッキから、プロダクトゴール（PG）の案を 2〜3 通り示し、選んでもらったものを `status: review` で書く（1.1）

**③ プロダクトバックログ**
- [ ] 仕様書の各章を PBI に分け、プロダクトバックログに置く。並び順は、価値・リスク・依存・大きさの表と推奨の案を付けて示す（1.1）。PBI は `未整理` でよい
- [ ] 「夜も眠れなくなるような問題」（問い 7）のうち、早く確かめたほうがよいものは、確かめるための PBI にして上のほうに置く案にする
- [ ] 「やらないことリスト」の「やらない」に入ったものは PBI にしない。「あとで決める」は `未整理` の PBI にして下に置く
- [ ] 上から 1〜2 スプリント分の PBI だけ、リファインメント（6.4）をして `準備 OK` の案にする
- [ ] 解決案（問い 6）のうち、PO の前提を変える決定（公開先・データの置き場所・費用など）だけ ADR の案にする。SA・TS は問い 6 の図をそのまま初版にし、細かい設計（GUI・TD）は作らない

**④ 完成の定義とまとめ**
- [ ] 完成の定義の初期版（7 章）を示す。心配ごと（問い 7）の手当てで、毎回確かめるべきものがあれば入れる
- [ ] 整合性チェック（OPTION 10.1・TEAM 4.1）を確かめる
- [ ] 要点と決めてほしいこと（インセプションデッキ・ゴール・並び順・上位の PBI・完成の定義）を解説つきで示して承認を求め、止まる
- [ ] 承認を受けたら `stable`・`verified` を書き、PR → マージを頼む
- [ ] `docs/06-sprints/sprint-00/retrospective.md` に短いふりかえり（YWT）を書く。次は「スプリント 01 を始めてください」を待つ

### 6.2 スプリントプランニング

決まりは ORIGIN 4.2。このチームでの手順：

開始：「スプリント <番号> を始めてください」

- [ ] `docs/sprint-<2 桁>-planning` で作業する
- [ ] 前のスプリントのレトロスペクティブの T を読み、入れる改善を決める
- [ ] **リファインメントで並び順を確かめる**：プロダクトバックログの表（順・ID・題名・大きさ・状態、ゴールの範囲の線）をメッセージに出してから、並び順がこのままでよいかを質問の画面で聞く。並べ替えるなら、どれをどこへ動かすかを 1 画面 1 問で聞く（v1.6。スプリント 08 の PO の指定：レビューでは聞かず、ここで聞く）
- [ ] **トピック 1（なぜ）**：Claude Code が、プロダクトバックログの上位の PBI とプロダクトゴールとのつながり、前回のレビューで出たこと、ゴールまでの見込みを示し、スプリントゴールの案を 2〜3 通り出す（1.1）。PO が価値をどう高めたいかを話し、スクラムチームで決める
- [ ] **トピック 2（何を）**：Claude Code が、前のスプリントの実績（完成した TASK の数）と今回使える時間（オーナーの予定も含む）から、入る量を示す。PO と話し合って `準備 OK` の PBI を選ぶ。足りなければその場でリファインメントする。**上位の PBI がつながっている**（同じ画面・流れ・部品を使い、片方だけだと途中の形になる）なら、複数の PBI を 1 スプリントに入れる案を出す。**別々の PBI** なら、1 スプリントに 1 PBI を基本にする。どちらかの理由を一言添える（v1.4。スプリント 06 の PO の指定）
- [ ] **トピック 3（どのように）**：Claude Code が、選んだ PBI を TASK に分ける（6.2.1）。必要なら TD・TST を直し、確認 ID を TASK に割り当てる（TEAM 5.5）
- [ ] TASK の順は、**価値の TASK（PBI の TASK）を先に着手**し、プロセスの TASK（TEAM・OPTION の改訂など）は、承認・マージ・CI を待つあいだに並行で進める（v1.6。スプリント 08 の案 4：プロセスの TASK を先にして、価値の着手が 12 分遅れた）
- [ ] 完成の定義の各項目を、何で確かめるか（道具がそろっているか）を点検し、表にする。足りなければ TASK にする（v1.1。スプリント 02 で fps の表示がなく最後の TASK で気づいたため）
- [ ] スプリントバックログを書き、整合性チェック（10.2・TEAM 4.2）を確かめる
- [ ] スプリントゴールと選んだ PBI を示して合意を求め、止まる
- [ ] 合意を受けたら、プロダクトバックログの状態を `スプリント中` にして PR → マージを頼む
- [ ] マージされたら最初の TASK から始める（6.5）

#### 6.2.1 TASK の分け方

- **1 TASK = 1 PR**、1 回の作業セッションで終わる大きさにする。
- PBI は縦に切る（画面・ロジック・保存をまたいで、PO が触れる形で 1 つずつ完成させる）。「全画面の見た目だけ」のような横の切り方をしない。
- 入る量は、前のスプリントの実績から決める。はじめのうちは少なめにし、実績で増やす。

**最初のスプリント**：スプリントゴールは「土台と、いちばん上の PBI の最小の形が、プレビューで動く」にする。土台の中身は TEAM 3.4。土台だけで終わらせず、PO が触れるものを必ず 1 つ入れる。

### 6.3 デイリースクラム（作業セッションの始め）

決まりは ORIGIN 4.3。Claude Code には「毎日」がないので、このチームでは **作業セッション（会話）を始めるたび、または再開するたび** に行う。オーナーの返事は要らない。

- [ ] スプリントバックログ・プロダクトバックログ・前回の記録を読む
- [ ] スプリントゴールまでの進み具合、このセッションでする TASK、妨げ（PO の決定待ち・CI の失敗など）を 3〜5 行で示す
- [ ] ゴールが危ういと分かったら、そのまま進まず PO に伝える（6.5 の「ゴールが危ういとき」）
- [ ] スプリントバックログの「作業セッションの記録」に 1 行足す

### 6.4 リファインメント（スプリントの間ずっと）

決まりは ORIGIN 5.1。このチームでは、スプリントの作業の 1 割ほどを目安に、次のスプリントの上位の PBI について行う。

PBI を `準備 OK` にする条件（0.2）：
- [ ] ストーリーと、PO が見て確かめられる受け入れ条件がある
- [ ] 受け入れ条件のすべてに確認 ID があり、TC に自動か手動か・どのファイルかが書いてある
- [ ] 画面に関わる PBI は、GUI がある（必要なら試作をプレビューに置いて実機で触ってもらう。TEAM 5.2）
- [ ] 大きさが S か M（1 スプリントに収まる）
- [ ] ADR の決定に反しない。新しく決めることがあれば ADR の案がある
- [ ] PO が承認した（`stable`・`verified`）

リファインメントの進め方（PO の支援。1.1）：
- [ ] Claude Code が、次の 1〜2 スプリント分の上位の PBI について、ストーリー・受け入れ条件・確認 ID・GUI の案を先に書く（書くときの注意は TEAM 5.1・5.2）
- [ ] あいまいな受け入れ条件は、確かめられる条件に言い換えた案を付ける
- [ ] 大きすぎる PBI は、利用者が触れる形のまま分ける案を出す（6.2.1 の「縦に切る」）
- [ ] プロダクトバックログ全体を見て、古い・重なる・ゴールに関係しない PBI の取り下げ・統合の案を出す
- [ ] PO に聞くことは、まとめて 1 回で聞く（オーナーの時間を守る）

### 6.5 作業

スプリントバックログの順に、Claude Code が自分で進める。TASK ごとの作業手順は TEAM 3.1。TASK が終わったら、指示を待たずに次の TASK へ進む。

**PBI の最後の TASK がマージされたら**
- [ ] 完成の定義（7 章）を 1 つずつ確かめる
- [ ] プレビューでの実機確認を案内する。**最初に「どのアプリで確かめるか」**（プレビューの URL か、ホーム画面のプレビュー版か）を確かめてもらう
- [ ] **見る前に、画面の右下の版の番号が、最後にマージしたコードの PR のマージのコミットと同じか**を確かめてもらう（文書だけのマージでは公開が動かないため。v1.3）。違えば、前の版が残っている（iPhone は Safari とホーム画面のアプリで別々に残る）。Safari はタブをすべて閉じて開き直し、ホーム画面のアプリは終了させて開き直してもらう（v1.1。スプリント 02 の実機確認で起きたため）
- [ ] 実機確認を頼むときは、TC の手順に加えて、**完成の定義の実機の項目（iPhone 11 の fps など）を必ず入れる**（v1.3。スプリント 05 で入れ忘れて聞き直したため）
- [ ] 実機確認は、項目ごとに「機器・やること・OK の条件」の表にして頼む（番号と短い言葉だけにしない）。fps は値を選択肢にし（例：60／58〜59／55〜57／55 未満）、最初の答えで値を受け取る（v1.5。スプリント 07 の案 1：番号だけで頼んで PO が中身を確かめに止まった・fps の値が抜けた）
- [ ] 結果（OK、または NG と様子・スクリーンショット）を受け取る。結果なしの「OK」は、結果を先に確かめる
- [ ] AC を書く前に、main と、手元で verify・E2E 全体を流したコミットの中身（`src`・`tests`・`e2e`・設定）が同じかを `git diff` で確かめる。同じなら手元の verify・E2E 全体を流し直さず、その結果を AC に書く。違えば流し直す（v1.6。スプリント 08 の案 5：同じ中身を 2 回流していた）
- [ ] `docs/pbi-<番号>-ac` で AC を `review` で書き、PR → マージを頼む。プロダクトバックログの状態を `完成` にする（受け入れはレビューで）

実機確認を PBI ごとにするのがオーナーの負担になるときは、スプリントレビューの前にまとめて行ってよい。

**ゴールが危ういとき**：ORIGIN 5.4（スコープの調整）・4.1（中止）に従う。このチームでは、Claude Code が気づいた時点で作業を止めて PO に伝え、PBI を戻す・分けるなどの案を出す。中止になったら、完成したものを見直し、残りをプロダクトバックログに戻して、新しいスプリントプランニングを行う。

### 6.6 スプリントレビュー

決まりは ORIGIN 4.4。このチームでの手順：

開始：スプリントの最後の日。Claude Code が案内する。

- [ ] `docs/sprint-<2 桁>-review` で作業する
- [ ] `完成` の PBI と AC、`完成` にならなかった PBI と理由を、`review.md` の案にまとめる
- [ ] スプリントゴールを達成したかを示す
- [ ] プロダクトゴールまでの見込み（完成した PBI の数の実績から、あと何スプリントか。幅を持たせて）と、決めてほしいこと（受け入れ・範囲を削るか）を 1 画面にまとめる（1.1）。並び順はレビューでは聞かず、次のプランニングのリファインメントで聞く（6.2）。PO が自分から足す・並べ替えるときは、いつでも受ける（9 章。v1.6）
- [ ] 関係者に見てもらう回では、案内文と聞くことの一覧を前もって用意する
- [ ] PO にプレビューで触ってもらいながら話し合う。見ること：できたもの・PBI ごとの受け入れ・プロダクトゴールまでの進み具合・まわりで変わったこと
- [ ] PO が受け入れた PBI の AC を `stable`・`verified` にする。受け入れなかった PBI は、理由を書いてプロダクトバックログに戻す
- [ ] 話し合いで出た感想・意見を PBI の案（`未整理`）に直し、並べ替えの案を付けてプロダクトバックログに入れる
- [ ] 本番に公開するかを PO に聞く（公開するならリリース 6.7 へ）
- [ ] インセプションデッキを見直すかを聞く（期間の見込みがずれた・トレードオフの優先順位が変わった・心配ごとが起きた、など。5.7）。範囲を削るか期間を延ばすか迷ったときは、トレードオフスライダーに沿った案を出す
- [ ] `review.md`・AC・プロダクトバックログをコミット（レトロスペクティブと同じ PR でよい）
- [ ] レビューのあと、レトロスペクティブの前に VSM（`docs/06-sprints/sprint-<2 桁>/vsm.md`）を作り、レトロの材料にする（8 章。v1.6。毎スプリント「レビュー → VSM → レトロ」）

### 6.7 リリース（いつでも）

開始：「リリースしてください」（バージョン番号）

- [ ] 公開するインクリメントの PBI が、すべて `完成` で AC が `stable`（PO が受け入れた）であることを確かめる
- [ ] 公開に入るもの・入らないもの・利用者にとって何が変わるかをまとめ、「本番に公開される」と伝え、入れたいものがないか聞く（1.1）

- [ ] 本番で全体を短く確かめてもらい、結果をそのスプリントの `review.md` に書く
- [ ] プロダクトバックログの状態を `リリース済み` にする

### 6.8 プロダクトゴールの達成（または放棄）と完了

## 7. 完成の定義（初期版）

完成の定義の決まりは ORIGIN 5.6。このチームの初期版を `docs/definition-of-done.md` に置く。変えるのはスプリントレトロスペクティブで、PO と合意して版を上げる（厳しくする方向に育てる）。

**TASK（PR）ごと**
- [ ] テストの名前の先頭に確認 ID があり、TASK の対象の確認 ID のテストがそろっている
- [ ] 手元で `npm run verify`（lint・単体・build・dist の検査・check:docs）と E2E が通る
- [ ] CI が緑
- [ ] 画面の変更は、PC と一番小さいスマートフォンの幅でスクリーンショットを見た
- [ ] TD・スプリントバックログが実装と合っている
- [ ] コミットメッセージ・PR が日本語で、解説が付いている（TEAM 1.1）

**PBI ごと**
- [ ] 受け入れ条件のすべての確認 ID に、自動テストの結果か実機確認の結果がある
- [ ] プレビューで実機確認をした（「確認できなかったこと」は AC に書いた）
- [ ] これまでのインクリメントと一緒に動く（E2E 全体が通る）
- [ ] AC が書かれ、整合性チェック（TEAM 4.3）を通った
- [ ] 一時的な診断のコードが残っていない

**本番に公開するとき（6.7）**
- [ ] 公開する PBI がすべて PO に受け入れられている
- [ ] 画面の版の表示と `package.json` の version が同じ
- [ ] README・権利やクレジットの表記がある

## 8. スプリントレトロスペクティブの書き方（YWT）

決まり（目的・検査すること・スプリントの終わり）は ORIGIN 4.5。このチームでは YWT で書く（0.2）。

置き場所：`docs/06-sprints/sprint-<2 桁>/retrospective.md`（ID・承認なし、check:docs の対象外）。Claude Code が案を書き、オーナーと話し合って足す。

```markdown
# スプリント <2 桁> のレトロスペクティブ（<日付>）

対象：スプリント <2 桁>（PBI-<番号>…、TASK-<番号>〜<番号>、PR #<番号>〜#<番号>）
スプリントゴール：<ゴール> → 達成／一部達成／未達成

## 言葉の表
| 言葉 | 意味 |
| :--- | :--- |

## Y（やったこと）
- 前回の T を守れたか（最初に確かめる）
- ORIGIN・OPTION・TEAM どおりに進めたか（タイムボックス・完成の定義・決める人の分担）
- PO の支援が役に立ったか（案は決めやすかったか・PO の決定を代わりにしていないか・並び順の案が作りやすさに寄っていないか）
- 完成した PBI と、作った・直したもの
## W（わかったこと）
- うまくいったこと、つまずいたこと（手戻り・CI の失敗・実機で見つかった問題）と原因
## ボトルネックの仮説
| 仮説 | 反対の仮説 | 確かめ方（どのメトリクスで見るか） | 前回の仮説は当たったか |
| :--- | :--- | :--- | :--- |
## メトリクスの見直し
- 増やすもの・減らすもの（使わなかったメトリクスはやめる）と理由
## メトリクス
| メトリクス | 決め方 | 前のスプリント | このスプリント |
| :--- | :--- | :--- | :--- |
## T（つぎにやること）
- 次に変えること。いちばん効くものを 1〜2 個選び、次のスプリントバックログに入れる
- OPTION・TEAM（TEAM 5 章の知見など）や完成の定義のどこに足すかも書く
```

- 1 項目 1〜2 行、全体で 1 画面ほど。
- エンジニアでないオーナーが読むので、**最初に言葉の表**（PBI・TASK・PR・確認 ID・CI など、本文に出る専門の言葉の言い換え）を置く。W のつまずきは「何が起きたか・なぜ・どうしたか」に分けて書き、T には理由を添える（TEAM 1.1 の解説の付け方）。このときは 1 画面を超えてよい。
- T のうち、いちばん効く改善は **次のスプリントのスプリントバックログに TASK として入れる**（ORIGIN 4.5）。OPTION・TEAM や完成の定義を変えるものは、次のスプリントプランニングの前に反映する（文書の冒頭の「版」を上げる）。ORIGIN は変えない。
- **ボトルネックの仮説・メトリクスの見直し**（v1.2）：毎回の議題にする。いちばん流れを止めているものの仮説と、その反対の仮説・確かめ方を書き、前回の仮説がメトリクスの値で当たったかを見る。メトリクスは仮説を確かめるために計り、使わないものは減らす。
- **メトリクス**（v1.2。スプリント 04 のふりかえりで PO が決めた）：毎回、次を表に埋める（POアシスタントが埋める。手で集めるのが重くなったら、集めるスクリプトを TASK にする）。数字は目標にせず、変わったときに原因を話し合うために使う。テストの数・コードの行数・コミットの数・対話の回数は計らない。
  - A. 完成した PBI の数・スプリントゴールの達成
  - B1. 待ちの記録：選択肢の質問・確認の依頼の前と、答えの後の時刻。スプリントバックログの「待ちの記録」に書き、作業が「止まった」か「並行」かも書く。**質問の画面を出す直前に、同じ応答の中で時刻を取る**。取れなかったら「推し量り」と書く（v1.3）
  - B3. マージの待ち：PR の作成からマージまで（GitHub の PR の時刻から）。「CI」と「CI のあと PO がマージするまで」に分けて出す（v1.3）
  - B4. 聞き直し・「確かめたい」の回数と、足りなかったこと（減らす目標にしない）
  - B5. 中断：長さだけを書く。待ちに入れず、評価しない
  - C. 1 回目で通った割合：CI の 1 回目の失敗の数・実機確認の 1 回目の NG の数・CI の flaky（同じ変更でやり直すと通る）の数
  - D. 前回の T を守れた割合と、変わったことを言葉で
  - F. リードタイム：PBI は準備 OK から完成までの作業時間（中断を除く）／TASK は前の PR のマージからその PR のマージまで
  - G. PO の手を通る回数（1 PBI あたり。マージ・確認・決定承認に分ける。決定承認は「決めること・承認」と「進め方の確かめ」（何を確かめたいか・始めてよいか、など）に分ける。v1.5）
  - H. 待ちの割合（B1＋B3 ÷ 作業の経過。中断を除く）を「全体」と「止まった分」で出し、並行にできた待ちの数も書く（v1.3）
  - I. 手戻りの数（確認・レビューのあとで足した TASK や直し。C の NG とは別）。E2E で起きる動きか、実機でしか出ない動きかを書き添える（v1.4）
  - J. 手動テスト（実機確認）の時間：回数・頼んでから答えまでの時間（テストそのものの時間の上限。気づくまでの時間などを含む）・NG の数（v1.4。スプリント 06 の PO の指定）
  - K. 待ちの内訳：待ちの記録の「種類」を「決定・承認／進め方の確かめ／実機確認／CI／CI のあとのマージ／機械（手元の verify・E2E・Pages の公開）」で書き、種類ごとの合計と割合を出す。機械の待ちも記録し、並行かを書く（v1.5。スプリント 07 の PO の議題「仕掛かり待ちの時間をより詳しく」）
  - L. TASK の状態の時刻：TASK ごとに、着手・PR 作成・CI 終わり・マージの時刻をスプリントバックログの表に書く（v1.5）
  - O. PBI の段階の時刻：①依頼 ②準備 OK ③最初の着手 ⑤最後のマージ ⑥公開の終わり ⑦実機確認 OK ⑧AC のマージ ⑨受け入れ。PBI を足すときに、依頼の時刻（時:分）を PBI のメモに残す（v1.5。スプリント 07 の PO の議題「VSM を作りたい」）
  - P. 段階ごとの %C/A：差し戻しや直しを「どの段階で見つけ、どの段階に戻したか」で記録し、段階ごとに差し戻しなしで通った割合を出す（v1.5）
  - VSM の段階の区切り：①依頼（PO）②リファインメント・プランニング ③TASK を作る ④PR・CI ⑤マージ ⑥公開 ⑦実機確認（PO）⑧AC の記録 ⑨受け入れ（PO）。本番の公開をするまでは ⑨ で終わる。PT（手を動かした時間）は「L の時刻のあいだ − K の止まった待ち」で出し、並行の分は二重に数えない。VSM は毎スプリント、レビューのあと・レトロの前に `vsm.md` に作る（v1.5。毎スプリントにしたのは v1.6、スプリント 08 の PO の指定）
  - 入れなかったもの：M（仕掛かりの効率。中断を含む値が圧力に読める）・N（仕掛かりの数。開発者が 1 人ではわかることが少ない）・Q（実機確認の PT。PO の手が増える）（スプリント 07）
  - やめたもの：E（カイゼン数。D の言葉にまとめた）・B6（PO が使った時間。取り方がなく B1・B3 と重なる）
- `summary.md`：Y（全体の数とスプリントごとの表：ゴール・達成・完成した PBI の数）、W（くり返し効いたこと・くり返し出たつまずきとどう直したか）、T（次のプロダクトで最初から入れること）。

## 9. プロダクトバックログの変更（いつでも）

変更の歓迎は ORIGIN 1.2 の原則 2、スプリント中のスコープの調整は ORIGIN 5.4。このチームでは、変更を「依頼の文書」ではなく **PBI としてプロダクトバックログに入れる**。PO が並べ直せば、それが計画の変更になる。

開始：オーナーが変更のメモを渡す（何を・なぜ・画面のイメージ）。思いつきの一言でもよい。Claude Code が PBI の形に直し、足りないこと（なぜ・誰のため）を聞く（1.1）。

- [ ] 仕様書の変更が要るときは、仕様書の版を上げ、改訂履歴に書く（PO の承認を受けてから）
- [ ] 新しい PBI を `未整理` で作るか、既存の PBI の版を上げて `review` に戻す。PBI の「メモ」に、影響の一覧（TEAM 4.6）を書く
- [ ] 並べ替えの案（どこに入れるか、何が後ろにずれるか）を示し、PO に決めてもらう
- [ ] すでに `完成`・`リリース済み` のものを変えるときは、直すための新しい PBI を作る（済んだ AC は書き換えない）
- [ ] **今のスプリントの中に入れたいとき**：ORIGIN 5.4 に従って PO と話し合う。スプリントゴールが危うくなるなら次のスプリントに回す（中止は ORIGIN 4.1）
- [ ] 選ばれたら、ふつうの PBI と同じくリファインメント（6.4）→ スプリント（6.2〜6.6）で進める

## 10. スクラムの文書の整合性チェック

文書の ID・sources・テストのつながりのチェックと自動化は TEAM 4 章。

### 10.1 スプリントゼロのとき

**仕様書 → インセプションデッキ**
- [ ] 10 の問いすべてに答えがあり、「オーナーに聞くこと」の印が残っていない
- [ ] やらないことリストが、仕様書の範囲（作るもの・作らないもの）と食い違っていない
- [ ] トレードオフスライダーの優先順位が重なっておらず、品質がスライダーに入っていない

**インセプションデッキ → プロダクトゴール・プロダクトバックログ**
- [ ] プロダクトゴールの sources にインセプションデッキと仕様書の版がある
- [ ] 仕様書の範囲（作るもの・作らないもの）と、やらないことリストが、そのままプロダクトゴールの範囲になっている
- [ ] やらないことリストの「やらない」に入ったものが、PBI になっていない
- [ ] 心配ごと（問い 7）のそれぞれに、手当て（確かめる PBI・完成の定義・「受け入れる」と決めた記録）がある
- [ ] 仕様書の各章が、どれかの PBI の sources にある（ないものは対象外と理由を書いた）
- [ ] 仕様書の受け入れ基準の各項目が、どれかの PBI の受け入れ条件になっている
- [ ] プロダクトバックログの行と PBI のファイルが 1 対 1 で、状態が同じ

### 10.2 スプリントプランニングの前

- [ ] 選ぶ PBI がすべて `準備 OK`（6.4 の条件を満たす）
- [ ] スプリントゴールが 1〜2 文で、選んだ PBI で達成できる
- [ ] 選んだ PBI の確認 ID が、すべてどれかの TASK の対象になっている
- [ ] TASK の依存の順と、スプリントバックログの並びが食い違っていない

## 付録 A. スクラムの言葉の言い換え（オーナー向け）

Git・CI などの言葉は TEAM の付録。

| 言葉 | 言い換え |
| :--- | :--- |
| スクラム | 短い期間で「作る → 見る → 直す」をくり返す、チームの進め方の決まり |
| プロダクトオーナー（PO） | 何を作るか・どの順で作るかを決める人（オーナー） |
| 開発者 | 作る人（Claude Code） |
| スクラムマスター | 決まりどおりに進むように手助けする役（Claude Code）。PO の作業の下書きや整理も手伝う |
| プロダクトゴール | このアプリで目指すいちばん大きな目標 |
| プロダクトバックログ | 作りたいものを、大事な順に並べた一覧 |
| PBI | プロダクトバックログの 1 行。作りたいもの 1 つ |
| リファインメント | PBI を小さく、詳しくして、作れる状態にすること |
| スプリント | 1 週間の区切り。毎回、触れるものを 1 つ以上作る |
| スプリントゼロ | 最初のスプリントの前に置く準備の期間。なぜ・何を・どう作るかをそろえる |
| インセプションデッキ | 作り始める前に、オーナーと一緒に答える 10 の問い |
| エレベーターピッチ | プロダクトを 30 秒で説明する短い文 |
| トレードオフスライダー | 迷ったときに、作る機能・期間・費用のどれを優先するかの順位 |
| スプリントゴール | そのスプリントで目指すこと |
| スプリントバックログ | そのスプリントで作るものと、作り方の計画 |
| TASK | 計画の 1 行。1 回の作業と 1 つの PR になる大きさ |
| インクリメント | スプリントでできた、使える状態のもの |
| 完成の定義 | 「できた」と言ってよい基準の一覧 |
| スプリントレビュー | できたものを一緒に触って、次に何をするか決める場 |
| スプリントレトロスペクティブ | 進め方をふりかえり、次に直すことを決める場 |
| タイムボックス | あらかじめ決めた時間の上限 |
| AC | PBI ごとの確認の記録（自動テストと実機確認の結果） |
