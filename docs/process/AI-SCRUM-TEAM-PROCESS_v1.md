## 1. 作業の決まり

| 決まり | 内容 |
| :--- | :--- |
| 承認は質問の画面かチャットで | 質問の画面の選択肢（「承認します」）か、チャットの「承認します」で受ける。はっきりしない返事は確かめる（v1.2） |
| PR ごとに区切る | 作業はブランチ → PR → CI が緑 → オーナーがマージ。ただし**記録の PR**（変えたファイルが `docs/06-sprints/` と `docs/07-increments/` の下だけの PR）は、CI が緑なら Claude Code がマージしてよい。コード・CI の設定・TEAM・OPTION・プロダクトバックログ・承認のある文書（PBI・GUI など）を 1 つでも含む PR は、オーナーがマージする。Claude Code がマージしたときも片付けは同じ（v1.3）。Claude Code のマージは、権限の決まりで `gh pr merge` を許しておく（設定はオーナーが行う）。許されていないとき・止められたときは、オーナーにマージを頼む（v1.5。スプリント 07 で auto mode に止められた） |
| 小さな文書の PR はまとめる | 同じスプリントの小さな文書の直し（記録・版の表記など）は 1 つの PR にまとめる。コードは 1 TASK ＝ 1 PR のまま。AC は受け入れの前に main に要るので別にする（v1.2） |
| ブランチ名 | 文書は `docs/<内容>`、機能は `feat/<TASK>-<内容>`、直しは `fix/…`、道具は `chore/…`。作業の前に main を最新にしてから切る |
| main に直接コミットしない | 手元の main へのコミットは、Git のフック（`.githooks/pre-commit`、`npm install` で有効）が止める。止まったら作業ブランチを切ってからコミットする（v1.1） |
| 承認のある文書の push | 承認を受けて `stable`・`verified` を書いてから push する（`review` のまま push すると CI が落ちる。4.5） |
| マージ = プレビューに公開 | main へのマージで、本番とは名前・アイコンを変えたプレビューに公開される。本番の公開はリリースの作業（3.2）でだけ行う |
| マージ後の片付け | **`gh pr view <番号> --json state` が `MERGED` であることを確かめてから**、main を pull し、作業ブランチを手元と GitHub から消し、プレビューの公開の実行と URL を確かめる（オーナーの次の指示を、マージの合図と思い込まない。未マージの枝を消すと PR が閉じる） |
| 名前の扱い | 了承をとっていない人の名前を公開リポジトリに書かない |
| 日本語で書く | Claude Code のメッセージ・コミットメッセージ・PR は、できる限り日本語（1.1） |
| 解説を付ける | エンジニアでないオーナーにも分かるように書く（1.1） |

### 1.1 言葉と解説

**日本語で書くもの**
- Claude Code のメッセージ
- コミットメッセージ。1 行目に何をしたかを短く書き、必要なら 1 行空けて理由を書く（1 コミット 1 目的）
- PR の題名・本文・コメント
- スプリントの記録（スプリントバックログ・レビュー・レトロスペクティブ）

**英数字のままにするもの**：ブランチ名・ID・ファイル名・コマンド。日本語にすると、道具によって文字化けしたり、入力しにくくなったりする。

**解説の付け方**
- 専門の言葉（ブランチ・PR・マージ・CI・スプリント・インクリメントなど）は、はじめて出たところで短く言い換える（例：「PR（変更を本流に入れてよいか確かめてもらう申請）」）。言い換えの一覧は、この文書の付録と OPTION 付録 A。
- 何をしたかだけでなく、なぜそうしたか・オーナーにとって何が変わるか・次に何をしてほしいかを書く。
- コマンドやファイル名をただ並べない。必要なものだけ示し、意味を添える。
- 決めてほしいことは、**質問の画面（選択肢）で 1 画面 1 問**にして、推奨と、選んだあとに何が起きるかを添える。答えが選択肢の言葉で決まる形にする（「OK」だけでは決まらない聞き方をしない）。2 問以上の画面では答えが抜けやすい（3 回あった）。承認（`stable` にするもの）は必ず単独で聞く。答えが抜けたら、推測で埋めずにすぐ聞き直す（v1.2）。
- **コマンドの実行の確認を求めるときは、リスクの評価を添える**（v1.1）。なし（読み取りだけ）／低（手元のファイルだけを変える）／中（GitHub に送る・PR を作る）／高（消す・上書きする。元に戻しにくい）と、一言の理由。

**文字化けを防ぐ**（Windows の PowerShell 5.1）：日本語のコミットメッセージ・PR の本文は、BOM なしの UTF-8 のファイルに書いて渡す（`git commit -F <ファイル>`、`gh pr create --body-file <ファイル>`）。GitHub でマージしたときに自動で付く題名（「Merge pull request #n …」）は英語になる。日本語にしたいときは、マージの画面で書き換えるか、リポジトリの設定で PR の題名を使うようにする。

## 2. 文書の管理

### 2.1 ID と、スクラム以外の文書

ID は `<PREFIX>-<種類>-<4 桁>`、ファイル名は `<ID>-<種類名>-ja.md`。欠番は使い直さない。スクラムの文書（IDK・PG・PBI・スプリントバックログ・AC・完成の定義）の置き場所と承認は OPTION 5.1。

| 種類 | 略 | 置き場所 | いつ作る | PO の承認 |
| :--- | :--- | :--- | :--- | :--- |
| system-architecture / technology-stack / architecture-decision | SA / TS / ADR | docs/02-architecture | 決める必要が出たとき | PO の前提を変えるものだけ（OPTION 2.1） |
| gui-design | GUI | docs/03-gui | 画面に関わる PBI のリファインメント | あり |
| technical-design | TD | docs/04-design | スプリントプランニングのトピック 3・実装中に、必要な分だけ | なし |
| test-strategy / test-case | TST / TC | docs/05-test | TST は最初のスプリント。TC は PBI を「準備 OK」にするとき | なし |

ID のないそのほかの文書：仕様書 `docs/specification.md`、再現開発仕様書 `docs/reproduction-specification.md`。

TASK の ID は `<PREFIX>-TASK-<4 桁>`（スプリントをまたいで通し番号）。

### 2.2 frontmatter

ID を持つ文書はすべて次の形にする。

```yaml
---
id: <PREFIX>-PBI-0001
type: product-backlog-item
title: タイトル画面から始める
status: review          # draft | review | stable
version: 1.0
updated: 2026-11-02
sources:                # 根拠にした成果物と、その版
  - <PREFIX>-PG-0001（v1.0）
  - docs/specification.md (v1.0) §7
verified: null          # 承認したら { by, at（+09:00） }
---
```

種類ごとに足す項目は OPTION 5 章（PBI の `theme` など）。

### 2.3 番号の決まり

- test-case の番号は PBI と同じ。AC の番号も PBI と同じ。
- 確認 ID は `<PREFIX>-TC-<4 桁>-<2 桁>`。自動テストは名前の先頭に確認 ID を書く。
- 非機能の test-case の番号の付け方は、最初のスプリントで TST を作るときに決める（あとから足す PBI とずれないように）。

### 2.4 版の上げ方

| 場合 | すること |
| :--- | :--- |
| 中身が変わる | 版を 0.1 上げる。承認のある種類は `status: review`・`verified: null` に戻し、再承認 |
| 上流の版が上がったが、中身は変わらない | sources の版の表記だけ直す（版・status・verified はそのまま） |

版の上げと、全成果物の sources の表記そろえは、スクリプト（`scripts/`）で行う。最初のスプリントで用意する（3.4）。

## 3. 作業の手順

### 3.1 TASK の作業

OPTION 6.5 で、スプリントバックログの順に TASK を進めるときの手順。

- [ ] main を最新にし、スプリントバックログに書いた名前でブランチを切る（1 章）
- [ ] TASK の「やること」と対象の確認 ID を読む
- [ ] テスト（名前の先頭に確認 ID）を書く → 実装する
- [ ] 手元で `npm run verify`（lint・単体・build・dist の検査・check:docs）と E2E を通す
- [ ] 画面の変更は、PC と一番小さいスマートフォンの幅でスクリーンショットを見る
- [ ] スクリーンショットで GUI の文書に書いていない見た目の問題に気づいたら、PR の前に PO に聞き、その TASK の中で直す（v1.2）
- [ ] 一時ファイル（撮影用のテストなど）は、リポジトリの中ではなく scratchpad に作る（v1.3）
- [ ] 設計と違う作りにしたら TD を直す。GUI・受け入れ条件と違ってしまうなら、作る前に PO に聞く
- [ ] スプリントバックログの TASK の状態を直し、同じ PR に入れる
- [ ] PR → CI が緑 → マージを頼む（マージ = プレビューに公開）→ 片付け（1 章）
- [ ] PO の確認・マージを待つあいだは、main に入れない下書き（次の TASK のテストなど）を並行で進め、待ちの記録に「並行」と書く（v1.2）

### 3.2 リリースの作業

OPTION 6.7 で、PO が本番の公開を決めたあとの作業。

- [ ] `package.json` の version を決め、画面の版の表示を確かめる
- [ ] プロダクトゴールの達成を確かめるリリースでは、仕様書の受け入れ基準のすべてに確認 ID と結果があることを一覧で確かめ、check:docs を厳しいモード（4.5）で通す
- [ ] README（使い方・権利やクレジットの表記）がそろっているか確かめる
- [ ] タグを付けて、本番の公開を動かすようオーナーに頼む

### 3.3 完了の作業

OPTION 6.8 で、プロダクトゴールを達成（または放棄）したときの作業。

- [ ] `docs/reproduction-specification.md` の第 1 部を最新の仕様書に、第 2 部を main の実装（設定・保存のキー・値）に合わせる
- [ ] 第 1 部が最新の仕様書と同じ、第 2 部の値が main の実装と同じであることを確かめる（4.4）
- [ ] README の内容（機能・コマンド・ファイル構成）が最新か確かめる

### 3.4 最初のスプリントで作る土台

OPTION 6.2 の最初のスプリントで、いちばん上の PBI と一緒に作る。

- CI（PR ごとに verify と E2E を動かす）
- プレビューと本番の 2 つの公開先（名前・アイコン・保存のキーを分ける。5.1）
- PWA の骨組み
- 画面への版の埋め込み
- テスト用の入口（5.3）
- `check:docs`（4.5）と、版を上げるスクリプト（2.4）
- test-strategy（TST）

### 3.5 実機で原因が分からないとき

推測で直すのは 1 回まで。次は、画面に状態を出す一時的な診断を入れ、記録を見て決める（PBI を完成にする前に消す）。

## 4. 文書とテストの整合性チェック

スクラムの文書どうしのチェック（インセプションデッキ・プロダクトバックログ・スプリントゴール）は OPTION 10 章。

### 4.1 いつも確かめること（すべての成果物）

- [ ] ID とファイル名が決まりどおりで、欠番を使い直していない
- [ ] sources に、根拠にした成果物の ID と版が書いてある
- [ ] sources の成果物が `stable` で、書いた版が今の版（仕様書は、引用した章がその後の版で変わっていないか）
- [ ] 本文から参照している ID・章番号・ファイルが実在する
- [ ] 上流の版を上げたら、それを sources に持つ下流をすべて見直した（直さないものも版の表記は直した）

### 4.2 スプリントプランニングの前（技術）

- [ ] 各確認 ID が、その TASK の時点でそろう機能だけで書ける（5.5）
- [ ] 画面に関わる PBI の GUI の部品・状態・メッセージを、どのモジュールで作るか決まっている
- [ ] ADR の決定（層の決まり・技術）に反する計画がない

### 4.3 PBI を完成にするとき（AC）

- [ ] テストの名前の確認 ID が test-case に実在し、test-case の確認 ID がすべてテストのコードか手動の手順にある
- [ ] AC の番号が PBI と同じで、sources に PBI・TC・TASK がある
- [ ] PBI の確認 ID が、すべて AC の結果か「確認できなかったこと」にある
- [ ] 結果の数値・文言が、テストの実際の出力と同じ
- [ ] PBI と GUI の文言（ボタン名・メッセージ）が、実装と同じ

### 4.4 完了のとき

- [ ] 再現開発仕様書の第 1 部が最新の仕様書と同じ、第 2 部の値が main の実装と同じ

### 4.5 自動化（`npm run check:docs`）

`scripts/check-docs.mjs` を最初のスプリントで作り、CI の verify にも入れる。

- **エラー**：ID・ファイル名・フォルダ／frontmatter の項目／実在しない ID／sources の版の違い／`stable` なのに sources が `review`／承認のある種類の `stable` に `verified` がない／テストの確認 ID が test-case にない／test-case の確認 ID がテストのコード（自動）か AC（手動）にない／プロダクトバックログの行と PBI のファイルが合わない／`完成` の PBI に `stable` の AC がない
- **厳しいモード**（`--strict`、プロダクトゴールの達成を確かめるリリース）：未実装・未記録も 0 に
- 承認待ちの間の「`stable` なのに sources が `review`」は正常（承認で消える）。`review` のまま push すると CI が落ちるので、承認のあとに push する。ただし AC は `review` のまま push してよい（受け入れはスプリントレビュー）。check:docs は AC の `review` をエラーにしない。
- Windows の PowerShell では `npm run x -- --flag` のフラグが届かないことがある。`node scripts/check-docs.mjs --strict` で直接動かす。

### 4.6 変更の影響の一覧

OPTION 9 章で、変更を PBI にするときに PBI のメモに書く。

| 区分 | 対象 | 直すこと |
| :--- | :--- | :--- |
| 仕様書 | §x | … |
| プロダクトゴール | PG | 変わるか |
| 承認のある成果物（再承認） | PBI・GUI など | … |
| 承認のない成果物 | TD・TC・TST | … |
| テストのコード／実装 | ファイル | … |
| 版の表記だけ直すもの | sources を持つ成果物 | 表記を直す |
| 直さないもの | 済んだ AC など | 理由（sources の表記は直す） |

- 洗い出しは、変わる章を sources に持つ成果物を grep する。**数値を変えるときは値そのものも grep する**。
- 項目を足したら、同じ部品・画面に触れる項目と見比べ、食い違いを承認の前に直す。
- 画面の配置を変えるときは、手の足し算ではなく、**今の画面を E2E の端末の大きさで測ってから**案を書く。
- 実装の途中で、承認済みの文書の直し漏れに気づいたら：その文書を `review` に戻し、影響の一覧に「あとで見つけたもの」の行を足し、再承認を受けてから push する。

## 5. 技術の知見（よく手戻りになるもの）

SDD-PROCESS v3 の 8 章の知見を、使う場面ごとに並べ直した。スプリントレトロスペクティブの T で足していく。

### 5.1 仕様書・PBI を書くとき

- 仕様書に版と改訂履歴を持たせ、成果物の sources に版を書く。
- 同じサイトにほかのアプリも載るなら、保存のキー・キャッシュを分けるアプリ識別子を決める。プレビューと本番も別のアプリとして分ける。
- PWA なら、更新の切り替え方（勝手に切り替えない・「更新」ボタン）と、起動に失敗したときの復旧を決める。
- README と、権利・クレジットの表記をいつ作るかを決める（PBI にしてプロダクトバックログに入れる）。
- 非機能要件（60 fps・入力の遅れなど）も、確かめ方（自動か手動か）まで書く。どの PBI にも関わる非機能要件は、PBI ではなく完成の定義に入れる。
- 数値の条件（点数・ボーナスなど）が、1 回の利用で届くかを、取れる幅を出して確かめる。

### 5.2 画面の設計と試作

**試作**：画面の大きさ・配置と主な操作だけの HTML を `prototype/` に置き、プレビューの URL で実機で触ってもらう。本物とは **名前・アイコンを変える**（取り違え防止）。

- スマートフォンで、操作する指で大事なものが隠れないか。ボタンは 44 px 以上か。一番小さい端末で 1 画面に収まるか。
- キーボードが出たとき・ノッチ・ホームバー・ホーム画面のアプリのステータスバー。
- アプリの名前がホーム画面で切れないか。文字が読めるか。
- **画面にアプリの版を出すかと、その場所**。
- 大きさの基準は、**E2E で使う端末の大きさ**も含めて確かめる（Playwright の「iPhone SE」は第 1 世代 320 × 568。基準が 375 × 667 なら `iPhone SE (3rd gen)`）。
- iPhone のタッチは CSS だけでは長押しの虫めがね・2 回タップの拡大が止まらない。操作する場所では `touchstart` の既定の動きと `gesturestart` を止めると決める。
- 黒い背景のフォームの部品（ラジオ・チェック）は、標準の見た目に頼らず CSS で描く。
- **触った操作で画面が切り替わるときは、指の下に新しいボタン・入力欄が出ないかを確かめる**。出るなら、出てから約 1 秒は受け付けない。iPhone では、同じ操作のクリックが、後から指の下に出た部品に届く（v1.4。スプリント 06 で、終わりの画面を触ると名前の画面の OK に届いて手戻りになった）。
- 入力欄とボタンに、送信のボタン（`form`・`type="submit"`）は使わない。送信が届くとページが読み込み直される（v1.4）。

### 5.3 設計

- ロジックは DOM・時刻・乱数に触れない作り（状態と入力から次の状態を返す関数）にし、単体テストで確かめる。乱数は種を外から渡す。
- 中身を E2E から読めないもの（Canvas など）は、テスト用の入口（`?debug=1`、body の data 属性、状態の読み書き・停止・ステップ実行）を設計に入れる。最初のスプリントの土台に入れる（3.4）。
- 文字の入力欄を置く画面では、ページ全体のキー操作が入力欄で効かないようにする。
- 画像から絵を作るときは、設計の前に画像を点で読み取り、その並びを設計とテストの期待値にする。
- 設計は、選んだ PBI に要る分だけ作る。先の PBI のための仕組みを先回りで作らない。

### 5.4 テスト

- **確かめ方を確かめる**（v1.2）：決まった値（設定・GUI の数値）を先に読んでから期待値を書く／境目は、ふちの少し内側と少し外側の両方を確かめる／確かめるもの（部品・テスト用の入口）がその場面にあるかを先に確かめる／前の TASK のテストの前提を変えたら、そのテストだけを直す。
- 実機でしか分からない項目（実機のブラウザ・ホーム画面のアプリ・音・読み上げなど）を、PBI を `準備 OK` にするときに手動の確認 ID として書く。**その手順が実機でできるか**まで確かめる（ホーム画面のアプリは URL を変えられない、など）。
- E2E は CI と手元でフォントが違う。文字の幅に頼らない。収まりの判定は行の高さを決め打ちにして余裕を残す。
- 時間を進めるテストは、偽の時計を止めてから進める（Playwright：`install` → `pauseAt` → `runFor`）。時間で変わる表示は、状態をそろえてから見るか操作の直後に見る。
- 状態で操作を分けるときは、1 回読んで分けず、端末で分けるか状態が変わるのを待つ。
- 物を置く位置は、1 ステップの移動量ではなく境目（接する位置）から決める。画面を開く関数は、前の状態が残らない開き方にする。
- 画素を読む E2E は、倍率が変わっても同じ結果になる場所を選ぶ。新しく描く物が読む範囲にかからないか、先に grep する。
- テストを置き換えたら、すぐ check:docs で確認 ID のテストが消えていないかを見る。
- E2E で画面を進める操作（タイトル・終わり・TOP10 など）は、その端末の実際の操作で行う（PC はマウスのクリック、iPhone はタップ）。キーで進めると、クリックやタッチでしか出ない不具合が隠れる（v1.5。スプリント 07 の案 3：スペースキーで進めていたため、PC のクリックで名前の画面に入る不具合が隠れていた）
- E2E の iPhone のまね（Playwright の WebKit）では、「同じ操作のクリックが後から出た部品に届く」動きは起きない。触って画面が切り替わる所は、手動の確認 ID（実機）に入れる（v1.4）。
- アプリのファイルを止めたり差し替えたりする E2E（`page.route`）は、Service Worker を止めて動かす（`test.use({ serviceWorkers: 'block' })`）。Service Worker が保存したファイルを先に出すと、止めたつもりの読み込みが止まらない。

### 5.5 確認 ID を TASK に割り当てるとき

- 確認 ID を PBI の番号で機械的に TASK に割り当てない。合意を求める前に、**各確認 ID が、その TASK の時点でそろう機能（前の TASK までに作るもの）だけで書けるか** を 1 つずつ点検し、書けないものは機能がそろういちばん早い TASK に移す。あわせて、確認 ID の準備・手順が使う部品（テスト用の共通の操作・画面どうしのつなぎ）が、どれかの TASK の「やること」に入っているかを見る。

### 5.6 実装

- PR の前に、手元で verify と E2E を通す（E2E が build したものを動かすなら、先に build）。
- 単体テストでは、置いた位置が前提を満たすこと（重なる・重ならない）を先に確かめてから本題を確かめる。同じ値で決まる規則は、値をちょうど与えて確かめる。
- テスト用の入口で場面を作るときは、狙う物以外を消して前提を先に確かめる。結果（点数など）は決め打ちせず状態から読む。
- 1 秒あたりの値（fps など）は、実際にたった時間で割って出す。
- PowerShell で、ファイルを書き換えるコマンドの出力を `Select-Object -First` で絞らない。絞った時点で前のコマンドが止められ、書きかけのファイルが空になる（v1.4。スプリント 06 で版を上げるスクリプトが PBI-0006 を空にした）。出力は変数に受けてから見る。
- 新しい絵や画面は、PR の前にスクリーンショット（PC と一番小さいスマートフォン）で形を見る。
- プレビューで実機確認をするときは、本番のアプリと取り違えていないかを最初に確かめる。版の切り替えを確かめる PBI では、最後の TASK をマージする**前に**、実機で今の版を一度開いてもらう。
