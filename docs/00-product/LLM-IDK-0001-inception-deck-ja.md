# 最終防衛線ミニ インセプションデッキ

スプリントゼロで、オーナー（PO）と Claude Code が「なぜ・何を・どう・どれだけ」をそろえるための 10 の問い。
Claude Code が案を書き、2026-11-02 のチャットでオーナーが答えた（Q1〜Q8）。

## 前提の決定（2026-11-02 のチャット）

| 項目 | 決定 |
| :--- | :--- |

## 1. 我われはなぜここにいるのか

- **いちばんの目的（Q1）**：**AI-SCRUM のプロセス（ORIGIN・OPTION・TEAM）を、実際のプロダクトで試す**。
- そのため、早いスプリントから「PBI → TASK → PR → CI → プレビュー → 実機確認 → AC → レビュー → レトロスペクティブ」をひと回りさせ、プロセスの改善点を見つけることにも価値をおく。
- プロダクトとしての価値：すき間時間に 1 プレイ 5 分前後で終わり、TOP10 に名前を残すためにくり返し遊べるゲームにする。
- 遊ぶ人：オーナー。オーナー以外に見てもらう予定は今はない。

## 2. エレベーターピッチ（Q2：遊ぶ人の目線）

すき間時間に手応えのある 1 プレイがほしい人向けの、『最終防衛線ミニ』は 1 面完結の防衛シューティングです。これは降ってくるミサイルを爆風の連鎖でまとめて落とす気持ちよさを 5 分で味わえ、長く続くアーケードゲームとは違って、1 回で終わり TOP10 に名前を刻めるところまでが備わっている。

## 3. パッケージデザイン

- **名前**：最終防衛線ミニ
- **キャッチコピー**：「5 分間、街を守り抜け。」
- **うれしいこと 3 つ**
  1. 1 面完結。1 プレイ 5 分前後で、すき間時間に終わる
  2. 1 発の迎撃で何発もまとめて落とす、誘爆の連鎖が気持ちいい
  3. TOP10 だけが残る厳しいランキング。入れば名前が光る
- **見た目の方向**：黒い夜空と独自の配色のドット絵。原作の黄色い地形・青い都市・赤い八角形の終了画面は使わない。細部は画面の設計（GUI）で PO が決める。

## 6. 解決案を描く

`docs/spec/ARCHITECTURE-TEMPLATE.md`（銀河戦争ミニの構成）を使う。初版の設計は `LLM-SA-0001`（システム構成）と `LLM-TS-0001`（技術スタック）。

```
 ┌──────────── 遊ぶ人の端末（PC / iPhone） ────────────┐
 │  ブラウザ                                             │
 │  画面（Canvas）・入力（キー／マウス／タッチ）          │
 │        ↓ 入力              ↑ 状態                     │
 │  ゲームのロジック（状態と入力 → 次の状態。乱数は種）    │
 │        ↓ 結果                                         │
 │  ランキング（TOP10）→ localStorage                     │
 └─────────────────────────────────────────────────────┘
          ↑ 読み込み（初回のあとはオフラインでも動く：PWA）
 ┌──────────── GitHub ────────────┐
 │ main にマージ → /preview/ に公開 │  ← プレビュー
 │ リリースのタグ → / に公開        │  ← 本番
 │ PR ごとに CI（テスト）          │
 └────────────────────────────────┘
```

テンプレートと違うところ：公開先を 2 つにする／音（audio 層）はまだ作らない／記録の書き出し・読み込みは作らない（あとで決める）。

## 7. 夜も眠れなくなるような問題

| # | 心配ごと | 手当て |
| :--- | :--- | :--- |
| ① | **スマートフォンの操作**：狙いながら 3 つの基地を撃ち分けるのが、指と小さい画面でやりにくい。指で照準が隠れる | 2 番目の PBI（LLM-PBI-0002）で、操作だけの試作を iPhone 11 で触ってもらってから本物を作る |
| ② | **権利**：原作に似すぎる。原作のスクリーンショットが公開のリポジトリに入る | 名前・絵・色・演出を独自にする。`docs/spec/*.png` は `.gitignore` で Git の対象から外す。build したものに原作の名前が入っていないことを check-dist で確かめる（完成の定義） |
| ③ | **仕様のあいまいさ** がゲームの手触りを決める（7a） | 各 PBI のリファインメントで、案と推奨を出して PO に決めてもらう |
| ④ | **難しさの調整**：1 面でクリアできるか、点が十分に開くか | ロジックを乱数の種つきで作り、自動で何度も遊ばせて点の幅を出す（TEAM 5.1）。調整の PBI（LLM-PBI-0011）を置く |
| ⑤ | **スマートフォンの動作の重さ** | 完成の定義に「iPhone 11 で動きがカクつかない（`?debug=1` の fps が 55 以上）」を入れる |
| ⑥ | **iPhone の Safari は、しばらく開かないサイトの保存データを消すことがある** → ランキングが消える | **受け入れる（Q6）**。ホーム画面に置けば消えにくいことを README に書く。書き出し・読み込みは「あとで決める」 |
| ⑦ | **本番とプレビューを同じ GitHub Pages に置く**：本番の Service Worker がプレビューのページまで扱い、取り違えが起きる | 名前・アイコン・保存のキー・キャッシュを分け、本番の SW がプレビューを扱わない設定にする。最初のスプリントの E2E で確かめる（LLM-SA-0001 §2） |
| ⑧ | **Android で確かめられない** | E2E の端末にも入れず、README に「動作を確かめた端末：PC・iPhone」と書く。受け入れる |

### 7a. 仕様書のあいまいな点（各 PBI のリファインメントで決める）

1. 敵の総数・ウェーブの数・1 プレイの長さ（案：6〜8 ウェーブ、約 5 分）→ LLM-PBI-0004・0011
2. 「全拠点の弾薬が尽きて着弾を阻止できなくなった時点でゲームオーバー」と「最終弾頭が消えた時点で都市が残ればクリア」が重なる場面 → LLM-PBI-0004
3. 敵が基地に当たったときの扱い → LLM-PBI-0003
4. 10 位と同点のスコアはランクインしない、でよいか（§5.1 と §5.3）→ LLM-PBI-0006
5. ネームエントリーをスマートフォンでどう操作するか → LLM-PBI-0007
6. スマートフォンの照準と発射の操作 → LLM-PBI-0002（試作で決める）

## 8. 期間を見極める

- プロダクトゴール（LLM-PG-0001）に入る PBI は **11 個**（ほかに次のゴールの候補が 2 個、「あとで決める」が 5 個）。
- オーナーの時間は 1 週間に 30 時間（Q8）と多いので、PO の確認待ちで止まることは少ない見込み。1 スプリントに入る量は Claude Code の作業量と実機確認の回数で決まる。
- 見込み：**プロダクトゴールまで 3〜5 スプリント（3〜5 週間）**。**最初に PC で 1 面を最後まで遊べる**のはスプリント 2〜3 の終わり。
- 実績のないときの推測。スプリント 1 の実績で見直す。

## 10. 何がどれだけ必要なのか

- **オーナーの時間**：1 週間に 30 時間まで（Q8）。プロセスの目安（3〜4 時間）より多いが、持続可能なペースのため、決めてほしいことはこれまでどおりまとめて聞く。
- **Claude Code**：開発者・スクラムマスター・PO の下書き
- **道具**：Git 2.51・GitHub CLI 2.103（ログイン済み）・Node.js 24・npm 11（手元で確認済み）
- **サービス**：GitHub（公開リポジトリ・Actions・Pages。無料の範囲）
- **お金**：0 円
